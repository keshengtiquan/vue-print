## 线宽单位 mm → px（只给方案，未实施）

需求：线条属性面板里「线宽」输入显示成 px，底层存储仍是 mm。老板要求先列方案。

调研结论：
- `element-property-config.ts` 的 `PropertyFieldConfig.displayUnit`（"pt" | "px"）机制**已经存在**，
  `ElementProperties.vue` 的 `displayValue()` 负责 mm→px/pt 换算显示（px 保留 1 位小数），
  `setField()` 负责反算回 mm 写入 store。text.borderWidth、table.cellStyle.borderWidth 已用 px 口径。
- 渲染层不用改：`LineElement.vue` 本来就是 `stroke.width(mm) * pxPerMm(scale)`；
  text/table 的 borderWidth 同理。底层 mm = 物理尺寸，px 只是输入口径。
- 换算常数：1mm = 96/25.4 px ≈ 3.7795px；1px ≈ 0.2646mm。素材默认线宽 0.5mm → 面板显示 1.9px（非整数）。

发现两个既有 bug（改线宽前要顺手修）：
1. `ElementProperties.vue` `setField()` 里 `field.min` 的 clamp 用的是 `rawValue`，
   紧接着 `if (field.displayUnit === "px") value = pxToMm(Number(rawValue))` 用 rawValue 覆盖了 clamp 结果
   → **带 displayUnit 的字段 min 完全失效**（输入负数也能写进去）。
2. number 字段模板 `:model-value="Number(displayValue(field)) || field.min || 0"`，
   底层值为 0 时会被 `||` 兜底成 min，面板显示与真实值不符。

给出三个方案（推荐 A）。待老板拍板项：min/step 取值、虚线间隔 dash 是否一起转 px、
素材默认线宽是否调成整数 px（1px = 0.2646mm）。

## line（线条）的几何事实 —— 「反转线条方向」是死操作（只给方案，未实施）

`ElementContextMenu.vue:157` 的 `reverse-line` 交换 `start`/`end`，渲染端 `LineElement.vue` 输出无标记 `<line>`，
首尾互换是同一段几何 → **像素级零变化**；dash 相位也因为图案是周期序列而无差别。

老板提议的「改成反转角度（rotation + 180）」**同样无效**，这是几何必然，不是 bug：
- 旋转支点 = 元素框中心（`ElementWrapper.vue:91` 写死 `transformOrigin: "center"`）
- **线段中点恒等于元素框中心**：素材默认 `width:30,height:4,start:(0,2),end:(30,2)`（`materials.ts:47`），
  中点 (15,2) 正好是框中心；缩放时 `start/end` 按 `finalW/startW` 同比例重算（`ElementWrapper.vue:301-305`），比例永久保持
- 所以绕框中心转 180° = 线段绕自身中点中心对称 = 映射回自身

唯一有效的「反转」= **绕线段中点镜像**：`start:{x:end.x,y:start.y}` / `end:{x:start.x,y:end.y}`（交换 x 不交换 y）。
对一条线段而言「水平镜像」与「垂直镜像」结果相同，不需要拆成两项。
镜像后端点仍在 [0,width]×[0,height] 内，不会跑出框。水平/垂直线镜像后与自身重合 → **必然无效，应把菜单项灰掉**。

根因：line **没有端点编辑能力**（无法拖拽端点改 start/end），旋转手柄只能转整体框，
所以用户实际上没有任何手段把一条水平线改成斜线。长期方案是给 line 加两个端点手柄 +
拖拽后把元素框吸附到线段包围盒；那时「反转方向」配合箭头才真正有意义。

方案：A 绕中点镜像 + 水平/垂直时禁用（推荐）；B 改 rotation+90（全可见但逻辑尺寸与视觉方向脱钩）；
C 直接删掉保留语义。待老板拍板。

## 给线段加端点手柄（已实施）

需求：老板反馈「我通过旋转改了线，他的坐标点根本没变，改 xy 也没用」—— 确认了 line 没有端点编辑能力。
改动全在 `ElementWrapper.vue`：

1. `DragMode` 加 `"endpoint"`；新增 `activeEndpoint` ref。
2. `transient` 加 `line: LineDraft | null` 字段（`wrapperStyle` 用 `t.line ?? {delta 叠加}`）。
3. 模板：`element.type === "line"` 时渲染 2 个端点手柄（`size-2.5` 实心蓝圆点 `bg-[#1a73e8]` +
   `cursor-crosshair`），**替代** 8 个缩放手柄；旋转手柄两者都保留。
4. `lineEndpoints` computed（拖拽中读 draft）、`ENDPOINT_MIN_THICKNESS = 4`、
   `onEndpointPointerDown`、`applyTransientEndpoint`。
5. `onEnd` 加 endpoint 分支（草稿整组写回，含 `rotation: 0`）；删掉原 resize 的 line 特例（已成死代码，
   因为线条不再渲染缩放手柄）。

### 核心几何结论（已在 MEMORY.md 立规矩）

- 端点全局都在包围盒的角或边中点上 → 缩放手柄与端点手柄**位置必然重合**，只能二选一。
- **框中心 = 旋转支点**（`transform-origin: center`）。拖端点必须重算包围盒 → 框中心位移 → 支点动，
  而「屏幕位移 → 局部位移」隐含支点不动 → 不处理的话没被拖的那一端会漂走（实测 θ=90° 可漂 9mm）。
- 解法：**把元素已有旋转烘焙进端点坐标**（换算到纸张 mm 空间算完再写回，rotation 归零）。
  线段视觉位置分毫不动（连续），框重新变回轴对齐包围盒，缩放分支的等比换算继续正确。
- 端点身份保持：拖哪个端点，哪个仍写进 `start`/`end`（「翻转线条」那类依赖首尾语义的操作才不错位）。

- vite 起服务后 curl 模块 HTTP 200；**回查 CSS 产物**确认 `size-2.5`、`cursor-crosshair`、`border-2`、
  `rounded-full`、`bg-[\#1a73e8]` 全部生成（Tailwind v4 按需生成，写错是静默失效）。
- 用 `node -e` 内联脚本跑几何算法：θ=0/30/90/137/270 五组用例，**锚点漂移 0mm、被拖端点跟手误差 0mm**。

  框应始终紧贴线（水平/垂直线时框有 4mm 的竖直/水平厚度）。

## 图片元素：属性面板加「上传图片」转 base64（已实施）

需求：图片属性里加上传入口，选中的图转 base64 显示，限制上传大小。老板先要计划，拍板 4 项：
5MB 直接拒绝 / 预览卡+折叠 URL / 保持宽度按比例适配高度 / 只做第一版。

改动 3 个文件（**渲染层零改动**，`ImageElement.vue` 一行没碰）：
1. **新增** `setting/element/ImageSourceField.vue`：预览卡（缩略图+文件名+像素+体积，含替换/移除按钮）
   或空态虚线上传区；折叠的「使用图片地址」URL 输入；错误/限制提示。emit `update:modelValue` + `loaded{width,height}`。
2. `element-property-config.ts`：`PropertyFieldType` 加 `"image"`，`PropertyFieldConfig` 加 `maxSize`/`maxDimension`；
   image 的 `src` 字段从 textarea 改成 `type:"image"` + 5MB/4096px。
3. `ElementProperties.vue`：`v-else-if="field.type === 'image'"` 分支（`:key="\`${field.key}-${element.id}\`"` 强制切元素重建，
   避免上一条文件的元信息串到另一张图上）+ `onImageLoaded()` 尺寸适配。

### 关键坑与决策（后续改这块必看）

- **base64 明文绝不能进 input/textarea**：几十万字符会让面板僵死。URL 输入框用 `isDataUrl ? "" : src` 受控，
  靠"绑恒等值 → Vue 跳过 patch"这条本项目已有套路，不打断用户输入。
- **三层"大小"是不同的量**：文件体积（5MB）/ 像素（4096px）/ base64 字符串（≈文件体积 × 1.37）。
  像素上限**按打印口径定**，不按网页优化：A4 宽 210mm 要 300dpi 需 2480px，4096 是满版出血余量，砍到 1600 会印糊。
- **先用 `URL.createObjectURL` 探尺寸再 `readAsDataURL`**：超像素的大图不必白读一遍 base64（几百毫秒）。
- **竞态双保险**：`runToken` 递增令牌（连续选文件只有最后一次落库）+ `onScopeDispose` 的 `disposed` 标志
  （组件卸载后到达的异步结果直接丢弃）。没有这层会出现"先选的大图后读完，把后选的小图盖掉"。
- **`input.value = ""` 必须在上传后立刻清空**，否则同一个文件连选两次不再触发 change。
- **base64 是必须而非妥协**：外链 URL 用于 canvas 导出/打印会污染画布（`toDataURL` 抛错），dataURL 同源不受限。
- 尺寸适配护栏：等比算出的高度超纸张（297mm）时，改为按纸张高度反推宽度，否则长图会竖穿出纸面。

## resize 吸附：方案已出，待老板拍板（尚未动代码）

诉求：拖 8 个缩放手柄改尺寸时也要吸附。

- **`snapAxis()` 不能复用**：它是为 move 写的，语义是"整体平移"（两条边都去够线，取最近的一组）。
  resize 的语义是"**只吸活动边、对边锁死**"，必须新增 `snapEdge(active, lines, tol)`（只吸单个坐标）。
- 改动面极小：新函数 + `applyTransientResize` 插入吸附步（先吸后夹 min）+ resize 分支 `setSnapKeys`，
  **全在 `ElementWrapper.vue` 一个文件**。高亮渲染层（`useSnapFeedback` / `MarginGuides` / `GuideLines`）零改动可复用。
- 我的推荐取舍（待拍板）：
  1. **仅 rotation 归一化后 ∈ {0,180} 时吸附**。非正交角上元素边不平行于参考线，对齐无意义；
     90/270 视觉框宽高互换需换轴反解，收益低。**更硬的理由**：旋转态下 resize 本身就会漂
     （改宽 → 框中心移动 → transform-origin 是框中心 → 对边跟着挪），在会漂的坐标系里吸附会吸到"看着对不上"的位置。
  2. Alt 临时关闭吸附（与 move 一致）；**不要占用 Shift** —— 留给将来的等比缩放。
  3. 容差复用 `MARGIN_SNAP_PX = 6`，不另起第二套手感常量。
  4. 吸附若把边推进 min（1mm）以内 → 回退成未吸附值，否则出现"吸住后尺寸卡在 1mm"。
- 待确认：线条端点拖拽要不要一并吸（我建议做，它已全程在纸张坐标里算，复用 `snapEdge` 最省事）；
  旋转 90/270 要不要支持（我建议不做）。

## resize 吸附：已实施（本节结论覆盖上一节的"待拍板"）

老板拍板"按你的建议来"：端点一并吸、90/270 不做。改动面 = `ElementWrapper.vue` + `statusLine` 一行文案。

- 新增 `snapEdge(at, lines, tol)`：只吸**单个坐标**。与 `snapAxis` **并存不合并**（语义不同，理由见 MEMORY.md「吸附」节）。
- `applyTransientResize(dxLocal, dyLocal, altKey)` 现在返回 hits 并做吸附：
  - e → `newW = s.value - newX`；
  - w → `newX = s.value; newW = (startEl.x + startEl.width) - s.value`（**用对边守恒反解**，右边缘恒不动）；
  - n / s 同理纵向。
  角落手柄两个轴各吸各的，一条命中不影响另一轴。
  - min(1mm) 分支是本次唯一新增的控制流：吸附把活动边顶过 min → **整轴退回自由值并清掉该轴 hit**；
    退回后若自由值本身仍 < min，再走原来的夹紧兜底。
- `applyTransientEndpoint(dx, dy, altKey)`：对 `moved.x / moved.y` 各吸一次并返回 hits。
  **这条路径不加轴对齐闸** —— 旋转已在第 ① 步烘焙进坐标，吸附是精确的。
- `isPaperAxisAligned()`：rotation 归一化 ∈ {0,180}（容差 `ANGLE_ALIGN_EPS = 1e-3` 度，旋转吸附产出的是浮点角）。
  读 `startEl.rotation` 快照而非 props，保证整个手势期间判定稳定、不中途翻转。
- 三条手势（move / resize / endpoint）都走 `setSnapKeys`，**高亮渲染层零改动**。

## 表格功能梳理（只出文档，未写代码）

背景：老板要开始做表格功能（判定为"项目的核心东西"），先梳理功能、不写代码。

**交付物**：`docs/table-feature-design.md`（新建 docs 目录）。含现状盘点、竞品对照、需求清单（老板 6 条逐条确认 + 我补的 9 个模块）、数据模型草案、10 个待拍板问题、分期建议。

### 现状（代码事实）

`TableElement` 只有 `rows / cols / cellStyle?`（全表一份样式），`TableElement.vue` 共 30 行，纯 `<table>` 渲染空单元格。右键菜单只有「增加一行/一列」（末尾 +1），属性面板「表格设置」一组、全表生效。

### 三个架构级缺口（文档的核心判断）

1. **数据模型装不下单元格**：无逐格样式、无 `colspan/rowspan`、无内容。且 `store.updateElement` 是**浅 Object.assign**、属性面板 `setField` 用点路径造 patch —— 二维数组无法用点路径表达，单元格写入需要独立 action。
2. **没有"表格内编辑态"，且与现有手势冲突**：现有 `editingId` 是元素级。表格要三层（元素 → 单元格 → 格内文本）。`ElementWrapper.onPointerDown` 在被点元素上按下就起 move 手势 → **点单元格会变成拖整张表**，必须让第 1 层手势给第 2 层让位。
3. **菜单/面板只有"类型"一维**：`getElementContextMenuConfig(type)`、`ELEMENT_PROPERTY_CONFIG[type]` 要升级成「类型 + 选中上下文」（表格体/单元格/行列头/多格选区/编辑中）。即**需求 4 其实是架构需求**。

### 待老板拍板的关键分歧（文档 §6，10 条）

最重要的是第 1 条**定位分岔：排版表格（静态，对标 Word）vs 数据表格（驱动，对标报表/标签软件）**。从 `repeatOnEachPage` 注释（"页眉/页脚/流水号类"）、mm 精度、`printable` 判断项目偏**单据/票据打印设计器**，表格大概率是「明细表」。建议：**按数据表格预留模型，第一期只做静态交互**。第 9 条（跨页表头重复）依赖"多页渲染"，而项目现在导出/打印还是占位 —— 需老板确认多页渲染的排期。

### 我替老板做了判断、需他复核的点（文档 §8）

A 实现 + B 预留；边框共享边"较宽者胜、同宽右/下者胜"；**不做单元格内富文本**（会让内容从 string 变文档树，成本极高）；合并用 `covered` 标记保留格而非删格（保索引=网格坐标）；元素缩放时列宽等比；行高列宽用 mm；合并只保留左上内容。

**新增 §1.5「数据表格对第一期的 6 条反向约束」—— 这是 v2 的核心价值，不是把"待定"改"已定"：**

1. **`height` 不是权威值，行高之和才是**（最关键）。现状 `TableElement` 是 `h-full w-full`（元素框权威），数据表格下必须翻转：`width ≡ Σ colWidths`、`height ≡ Σ rowHeights`。派生语义：拖元素手柄→等比缩放全部行列；拖分隔线→只改相邻两行/列、**元素框不动**。**若第一期写成"行高按百分比分配 + CSS 拉伸填满框"，接数据时几何层要重写。**
2. 单元格内容从一开始就是**可含占位符的文本**（`{品名}` 原样渲染，不加校验/转义），**不要拆成"固定文本/绑定字段"两种结构**——混排要拼接，越往后越难拆。
3. **行角色字段进模型**（header / detail / summary / normal），第一期全 normal，但数据版靠它区分"明细模板行"与"表头行"。成本是一个可选字段。
4. **行高列宽带模式**（`fixed`/`atLeast`/`auto`），不只存数值。`atLeast` 会打破约束 1 的强等式 → 元素 height 变"设定值"，实际取 `max(设定值, 内容所需)` 并回写。
5. 溢出策略 → 默认**自动换行 + 撑高行**；明确排除"溢出到相邻单元格"（数据一长就串列，静态期能用、数据版必崩，第一期就别做免得上瘾）。
6. **分页是前置依赖**：数据表格必然跨页，但项目**连多页渲染器都没有**（导出/打印还是占位）。已在 §6.2 列为**最要紧的待确认项**。
