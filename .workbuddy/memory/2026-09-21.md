## 预览 + 自动分页：设计文档（`docs/preview-design.md`）

老板指令：做预览（显示真实数据）+ 自动分页，先写设计文档再动手。**本轮只写文档，零代码改动。**

写文档前的代码复盘，三个关键发现（都写进文档了）：

1. **自动分页的真实触发源只有一个：表格明细行按数据行数生长。**
   画布是单张纸、元素坐标绝对 ⇒ 元素"超出纸张"在设计态当场看得见。
   所以「自动分页」与「表格明细行扩展」是同一件事的两半 —— 只做分页引擎等于没有输入。
   → 文档把 P0（分页引擎 + 渲染态）与 P1（明细行扩展）分开，但建议同轮做。
2. **`repeatOnEachPage` / `printable` 是"有 UI、零消费"的字段**
   （`ElementProperties.vue` 第 178–201 行暴露了开关，渲染层全仓 0 处读取）。
   按 §11.16 判据这属于"该删"的一类；预览是它们的第一个消费者 —— 要么让它生效，要么摘掉开关。
   `allowBreakAcrossPages` 则是"无 UI、零消费"。`renderTemplate` / `buildRowContext` 同样零调用点，
   文档里全部给了归宿（"接缝不是遗漏"这条口径继续成立）。
3. **预览不能复用 `dataBinding.run()`** —— 它会把全量数据写进 `state.samples`，
   等于用打印数据污染设计态样本（20 行）。预览另开 `store/modules/preview.ts`。

文档的核心设计判断（待老板拍板，§10 共 10 条）：

- **分页 = 绝对坐标 + 跨界顺延**，不做流式重排。第 1 页 ≡ 设计态（`u = y - p*H`，p=0 时恒等）。
  只有"页内放不下"才移动（唯一的移动来源是一个 `while` 循环），顺延后钳到内容区顶。
  顺延可能留页底空洞，明确接受，进警告条。
- **分页引擎是纯函数**，不 import Vue / 不 import store，不依赖 DOM 测量（可预测、无闪烁、可复用）。
  代价：文本溢出按框裁切（与设计态一致）。
- **预览不复用设计态元素组件**（927 行的 `TableElement` 交互太重），
  但**算 CSS 的纯函数必须抽到 `render/style.ts` 共享** —— 两个视图只差一个 `pxPerMm` 缩放因子。
- 缺值 `onMissing: "blank"`（打印所见）+ **占位符体检清单**进警告条（把静默空白变成可见清单）。
- 页码变量本轮就能做：`systemVariables()` 已支持 `pageIndex`/`pageCount`，零新增渲染逻辑。
- `sys` 注入需要一个口子：新增 `useDataBinding.renderContext(el, row, sys)`，`designContext` 委托它。
- 新写了三条看门狗 grep（预览层不得读设计态视图状态 / 分页层必须纯 / 渲染值入口唯一）。
- 额外建议了首个"Node 自检脚本"（不装测试框架，30 行断言）来验分页，**待老板批准**。

文档落点：`docs/preview-design.md`（11 节，含 §7 改动清单、§8 分期、§10 待拍板 10 条、§11 验证方式）。

### 本轮踩到的两个坑（值得记牢）

1. **Vue 模板属性值里不能出现裸 ASCII 双引号，也不能出现 `/* */` 块注释。**
   `TableElement.vue` 里写 `:class="[ /* 说明…第 1 行是"表头"… */ x ? 'a' : '' ]"` ⇒
   属性值被那个 `"` 提前截断 + `/*` 被 tokenizer 当标签结束，报出一串**位置全不对**的错
   （`stateInAttrName` / `Illegal '/' in tags`），vite 只返回一个没有行号的 500 HTML。
   排查正解：**用 `@vue/compiler-sfc` 的 `parse()` 拿 `errors[].loc`**，一次定位到行。
   → 已沉淀成 `scripts/check-templates.mjs`（零依赖，扫全仓 125 个 `.vue`，1 秒）。
   中文全角引号（「」“”）没事；要写长注释就放属性外或 `<script>` 里。
2. **占位符字面量的构造点必须唯一，且要放在纯函数层。**
   原设计说唯一构造点 = `useDataBinding.fieldToken()`，但**读取侧**（列映射规范化）也要拼 `{...}`，
   而读取侧不能引 composable（会毁掉纯函数层能被 Node 直接跑的地基）。
   就地拼的实测后果：`inspect.ts` 无条件包 `{}`、`PreviewTable` 加了"已是占位符就不包"的判断 ⇒
   **列映射直接写整段 `{订单明细.品名}` 时，预览渲得出值、体检却报"字段不存在"**。
   → 字面量构造下沉到语法权威模块 `lib/template.ts` 的 **`makeFieldToken(field, dataSetName?)`**，
   `useDataBinding.fieldToken()` 变成"解析 dataSetId → 调它"的薄壳。
   `grep -rn '`{\${' src` 现在恰好 1 行。

## 晚 21:15 列映射下拉与拖拽字段显示不一致（老板截图指出）

- 症状：明细行格子拖了 `{数据集1.username}`，预览取数正常（格子为准），但「列映射」下拉全显示「不映射」。
- 根因：下拉只读 `columnFields`（兜底声明），不读格子 `content`；拖拽写的是格子。取数规则没坏，坏的是显示。
- 修法（`BindingSection.vue`，详见 `docs/preview-design.md` §12.6）：
  1. 下拉显示生效映射：明细行格子恰好单一占位符 → 显示该字段（格子驱动）；否则回落 `columnFields[c]`。混排/覆盖格/前缀异数据集不算格子驱动。

  3. 失效字段动态补选项「字段名（字段已失效）」，不再伪装成「不映射」。
- 验证：check-templates 125 零错、check-paginate 51/51、eslint 0、vite+curl 200。待老板手点：拖字段→看下拉；下拉换字段/选不映射→看格子。

## 晚 22:15 修复行高自适应卡死 bug（老板实测：表格超一页死循环）

- 症状：comments(500行超一页) + 自适应 → 卡死；users(不超页)正常；调高行高让 users 也超页 → 也卡死。即表格跨页就死循环。
- 根因两层：① measure 用 getBoundingClientRect 得亚像素浮点，reportRowHeights 原用 !== 逐位比较 → 0.001mm 差异被当"变了"→ 写 store→重排→再 measure→无限；② 跨页时分页器按行高切分，行高微变让"每页放几行"在边界横跳，rows 数组每次不同 → watch 再触发 measure，分片行数↔行高互喂。
- 修法（双保险）：measure 量化到 0.1mm；reportRowHeights 改容差 >0.1mm 才写。量化后行高离散稳定 + 文本换行只由列宽/字号决定(与行高无关) → 环必然收敛。
- 未加保险丝：量化+容差已从根消除亚像素噪声，真机复现才加。
- 验证：check-paginate 55/55、check-templates 零错、eslint 0、vite 200。待老板用 comments 接口真机复验：开自适应不应再卡死。

## 晚 22:20 行高自适应卡死第二次修复（上一轮浮点假设是错的）

- 老板复验仍卡死，证明上轮"浮点精度"非根因。重新通读反馈环，找到**两个真正死循环源**：
  1. **watch deep 比较含函数的 ctx**：`watch(() => [props.rows, pxPerMm], deep)`，而 rows 每项 ctx 含 `get`/`getSys` 函数、`toItemView` 每次重算新建 ctx（函数引用也是新的）→ deep 深比较永远"变了" → watch 无限触发 measure（querySelectorAll+getBoundingClientRect 强制回流，500行跨页直接卡死）。
  2. **reportRowHeights 整表替换清零**：跨页时每个分片只测到本片模板行、未测到的填 0，后上报的片把先上报片的有效值覆盖成 0 → 行高在 15↔0 横跳 → 分页永不收敛。这才是"跨页才卡、不跨页正常"的精确解释。
- 修法：
  - watch 改监听 `rowsSignature()` = `props.rows.map(r=>r.templateRow).join(",") + "|" + pxPerMm`（原始值，=== 比较，浅快，且正是"撑高会变"的结构输入）。
  - reportRowHeights 改**逐模板行取 max 合并**（0 不参与覆盖），单调递增必收敛。
- 收敛性：取 max 单调 + 有上界(内容自然高) → store 值稳定 → 分片稳定 → 签名稳定 → watch 停。
- 验证：check-paginate 55/55、check-templates 零错、eslint 0、vite 200。待老板 comments 接口真机复验。
- 教训：反馈环卡死别急着怪浮点，先查 watch 的触发条件（deep+函数引用是经典坑）和数据合并语义（整表替换 vs 逐行合并）。

## 晚 22:27 修复"一页没占满就换页"（§8.6 修复引入的新 bug）

- 卡死已解（watch 签名 + max 合并方向对了），但老板截图：每页只放 2 行明细、半页空白就换页。
- 根因：§8.6 修复时把 measured 改成"按模板行号聚合取 max"，前提"同模板行自然高只由内容+列宽决定"对明细行**不成立**——每份记录不同（body 有长有短）高度天差地别。最长那条的 95mm 被强加给所有明细 → 分页按 95mm/行切（每页 2 行就换）→ 渲染按各自自然高画（70mm）→ 半页空白。分页口径 ≠ 渲染口径。
- 修法（5 文件）：PreviewTableRow 加 index（展开下标）；toItemView 传 index；measure 按 [下标, mm] 稀疏对上报、签名改展开下标序列；store.reportRowHeights(tableId, pairs) 逐下标 max 合并+扩长；expand.expansionRowHeights 改回 measured?.[i]。撑高告警改按模板行聚合实例 max（500 条没法读）。
- 断言 §16 重写：16.2「两份明细各用各的实测」即本次回归断言；新增 16.5 稀疏回落。56/56、check-templates 零错、eslint 0、vite 全 200、看门狗干净。
- 教训沉淀：明细行高度必须逐实例（展开下标）测量，模板行维度只对内容恒定的行（表头/尾行）成立。"测量值按什么维度聚合"要跟"渲染时高度由什么决定"严格同口径。

- 架构教训（值得沉淀）：给"先分页后渲染"的架构加"渲染后才可知"的输入时，别把测量塞进渲染流程（成环）；用独立的隐藏测量层把"算"前置，保住单向数据流。

## 深夜（续）测量层"只生效一行"：DOM 与行序列错位（第二页仍从 26 开始）

- 数字取证：fixed 断点 32（31 条/页）、atLeast 断点 26（25 条/页）。若实测完全没生效断点应仍为 32 → 实测**只生效了一行**（展开下标 1，≈50mm），其余 500 行回落声明高 8mm —— 与 26 精确吻合。
- 根因：测量触发用 watch(rowsSignature)+nextTick，watch 触发时 props 已变、rowViews（computed）已是新 502 行，但组件 DOM 还没 patch → trs（旧 3 行）与行序列错位，只有 trs[1] 存在撞对，其余被 if(!tr) return 跳过。"watch 时机 = DOM 已更新"只是碰巧成立不是保证。
- 修法（渲染驱动替代事件驱动）：测量改 onMounted+onUpdated（onUpdated 保证 DOM 刚按当前 props 更新完）；trs.length≠rowViews.length 时本轮作废+console.warn（宁可漏测不报脏数据）；row.index 非法跳过；store.reportRowHeights 拒收非整数下标（防 undefined 写脏键）；新增 measureDiagnostics（应测/已测）显示到警告条 —— 测量层死活一眼可见。
- 无环确认：measured 变化不回流测量层渲染输入（expansions 只依赖数据+声明），MeasureLayer 不重渲染不触发自身 onUpdated。
- 验证：56/56、126 零错、eslint 0、vite 4 模块 200（首次 502 是系统代理拦 localhost，--noproxy 直连即 200，环境坑）。
- 待老板复验：comments 接口开自适应，警告条应显示"已测 500+/500+ 行"，第 2 页应从第 6 条左右连续开始。

## 深夜（再续）"自适应像没生效"真凶：RowView 丢了 index（§8.10）

- 老板两张截图：fixed 第2页从27开始（正确基线）；自适应只画得出5行、6-26"消失"、第2页**仍**从27开始 → 分页器在两种模式下用同一套声明高 → 实测值从未上报。
- 根因①：measure() 用 row.index 上报，但 rowViews 构造的 RowView **没有 index 字段** → row.index 恒 undefined → 上轮加的防御 `if (!(row.index >= 0)) return` 把每一行都拦下 → 上报永远为空。诊断条其实一直显示"已测 0/500"，改完没看读数，教训：修完触发时机必须看"测到了什么"。
- 根因②（store）：reportRowHeights 的 max 合并是旧"多分片上报"架构遗产 → 行高只增不减（列宽调宽/文本删短后压不回去）。测量层现在是唯一上报者+全量覆盖 → 改整表替换（0.1mm 容差稳态零重排）。
- 修法：RowView 补 index；measure 上报全量数组（ceil(−1e-6) 量化：量出值≥自然高 → 分页永不越边距线）；渲染态 atLeast 行最小高 = max(声明,实测) 与 expansionRowHeights 同式 → "分页以为多高画出来就多高"；测量态刻意不吃实测（否则量不到变矮）。
- 关键认知：paginateBreakable 的逐行累加循环**本来就是**老板要的"一行一行画、放不下换页"，坏的只是输入。分页引擎 56 断言全程未动。
- 验证：56/56、126 零错、eslint 0、vite 3 模块 200。待老板复验：自适应后每页按真实行高占满换页、第2页从第6条连续开始、警告条诊断应显示 500/500。
