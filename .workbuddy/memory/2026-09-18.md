## 关键的实现判断（都写进 MEMORY.md 了）

1. **渲染放弃 `<table>`** —— 决定性理由：`<tr>` 的 `height` 是"最小高度"，内容一多行自己就涨，做不到 mm 精确行高。改用绝对定位 div 网格后，选区/分隔线热区与渲染共用同一套前缀和几何。
2. **边框冲突规则必须双向对称** —— 同宽取"下/右"者，若两个方向不对称，相邻两格会各画各的、不同色的两条线叠在一起。
3. **`updateTable` 整包替换** —— 逐格赋值会触发 N 次响应式更新，拖分隔线那种每帧改写的手势会被拖垮。
4. **删除行列前先拆开跨线的合并格** —— 不拆的话 `rowspan` 与实际占位对不上，网格静默错位（比拆开难查得多）。

## 明确没做（已写进文档 §9.2）

非连续选区、`atLeast` 行高撑高、双击自适应列宽、键盘导航、单元格剪贴板、跨页表头重复、斜线表头、格式刷、条码/二维码。

其中 `atLeast` 单独留一批的理由：它是一条**测量回路**（量内容 → 改行高 → 改元素框 → 重渲染 → 再量），写成每帧跑就是死循环，需要只对 atLeast/auto 行生效的 observer + 写入前收敛判断，值得单独做对。

## 三处与文档的有意偏离（需老板复核）

1. 旋转态下**允许**拖分隔线（文档建议禁止），只是不吸附 —— 局部坐标换算精确，无漂移风险。
2. 渲染用绝对定位 div 而非 `<table>`（实现层决定，数据模型不受影响）。
3. 默认单元格字号定为**五号（10.5pt）**，让面板 pt 档位与实际值对得上。

## 追加（同日下午）：渲染层改回 `<table>`

老板反馈"感觉做的不是很好"，明确要求用 `<table>`，不要 div 模拟。**推翻本文档上面的判断 1 与偏离 2**（按项目约定：老板指定了方案就在该方案内解决坑，不换方案）。

**关键认知修正**：v3 说"`<tr>` 的 height 是最小高度、表格标签做不到精确定高"——**只对了一半**。`<tr>` 的高度是精确的，**前提是单元格里没有流内内容**。做法：内容层 `absolute inset-0` + `td { position: relative }`，td 的"内容高度"归零，行高完全由 `tr` 的 height 决定。配套 `table-layout: fixed` + 显式 `<colgroup>`（auto 布局下内容会参与列宽计算，文字一长列就变宽）。

**改动**：
- `TableElement.vue` 渲染层重写：`<table>` + `<colgroup>` + `tbody`；td 直接设 border，四边交给 `border-collapse: collapse` 合并。`rowViews` 按行分组（网格坐标 → tr 的映射在渲染前定好）。
- `model.ts` 删除 `resolveBorderEdge` / `resolveCellBorders` / `opposite` / `cellRect` / `CellRect`。冲突解析交给浏览器后，那个"必须双向对称"的隐患从根上消失。`colOffsets`/`rowOffsets` 前缀和**保留**（选区框、热区、把手是相对表格定位的浮层，无表格布局可依托）。
- 冲突规则变为 CSS 规范：更宽者胜 → 样式优先级 → 靠前者（左上优先）。与文档原定的"同宽取右/下"不同，**以浏览器为准**。

**收益**（比 v3 更好，不只是妥协）：**为"表头行跨页重复"留下唯一可行路径** —— 前 N 行挪进 `<thead>` 即可逐页重复，浏览器打印引擎对 table 有原生分页支持，div 网格永远拿不到；共享边冲突不必自己裁决；DOM 语义化（导出/复制/打印读得懂）。

**代价**：拖列宽时浏览器重跑表格布局算法（小表格无感）；内容超出仍被 `overflow: hidden` 裁切（`atLeast` 未做，与 v3 同）。

**顺带发现**：用 table 后 `atLeast` 的实现回路**变短**了 —— 对 `atLeast` 行不设 tr 的 height，浏览器自己撑开，只需读回实际行高写进 `rowHeights`，从"测量内容→推算"退化为"读取浏览器算好的结果"。已补进文档 §9.4。

验证：curl 全部改动模块 200（首个 000 是冷启动未就绪，复测正常）；编译产物确认含 `table`/`colgroup`/`tbody`/`rowspan`/`colspan` 与 `tableLayout`/`borderCollapse`；eslint 0 错误。文档同步到 v4。

## 追加：修"点其他单元格退不出文本编辑"

老板反馈：双击能进单元格编辑，但点其他格时不退出。

**根因**：`onCellPointerDown` 里非编辑格那条路径上的 `e.preventDefault()` —— 浏览器"按下鼠标即转移焦点"正是被它拦掉的默认行为，textarea 一直持有焦点 → `onCellBlur` 永不触发 → 编辑态挂住。

**修复**：在 `isEditingCell(view)` 早退之后、`preventDefault()` 之前显式 `store.stopCellEditing()`。内容由 `@input` 实时写入 store，因此不需要额外提交动作。

**这条值得记住的规律**（已写进 MEMORY.md）：*编辑态退出有两条路 —— "失焦"和"显式收"。只要某条交互路径里 preventDefault 了，那条路径就必须走显式收。* 同一个根因这是第二次踩（第一次是元素级文本编辑的"禁止在编辑态 preventDefault 画布"）。

验证：curl 该模块 200、eslint 0 错误。**未做浏览器验证**，需老板确认点其他格确实退出、且双击别的格能直接进新格编辑。

## 追加：修"右键菜单点别的单元格不消失"（架构级）

老板反馈：选中单元格后右键开菜单，再左键点另一个单元格，菜单不消失。

**根因有两层，叠在一起才显形**：

1. **reka 的关闭监听在 document 的冒泡阶段**（`DismissableLayer` → `usePointerDownOutside`，
   `addEventListener("pointerdown", handler)`，读完源码确认**没有 capture**）。而本项目元素内部
   pointerdown 处处 `stopPropagation`（挡的是画布根的"点空白取消选中"）→ 事件到不了 document
   → 菜单关不掉。**这是"用 stopPropagation 达成具体目的"的代价：它顺手切断了 document 层的一切监听。**
2. **`ContextMenu` 默认 `modal: true`** → `MenuRootContentModal` 传
   `disable-outside-pointer-events: open` → DismissableLayer 把 `document.body` 的
   `pointer-events` 设成 `none` → 菜单开着时画布上什么都点不中（事件目标退化成 `<html>`）。

**修复（三条独立措施，互为兜底）**：
- 画布根改判落点：`ElementWrapper` 去掉 `@pointerdown.stop` + 根节点加 `data-design-element`；
  `designPanel/index.vue` 的 `deselect` 改成 `onRootPointerDown`，用 `closest` 判断命中元素就放行。
  表格的单元格 / 分隔线 / 行列把手同样去掉 stop（它们在表格编辑态下靠 `ElementWrapper` 的
  `tableEditing` 分支让位，stop 本来就多余）。`GuideLines`、textarea、各手势手柄的 stop **保留**。
- 两处菜单加 `:modal="false"`（桌面右键菜单本就该非模态）。
- 新增 `designPanel/components/ContextMenuAutoClose.ts` 哨兵：放进 `<ContextMenu>` 内，
  用 reka **公开导出**的 `injectContextMenuRootContext` 拿 `onOpenChange`，在 document 的
  **capture 阶段**监听左键（capture 是路径第一站，不受任何 stop 影响）；落点在
  `[data-dismissable-layer]` 内则不关，保护菜单项 click。渲染函数返回 null，零 DOM。

**顺带**：`ElementWrapper.onPointerDown` 里那句"表格内部的 pointerdown 已经 stopPropagation，
走不到这里"的注释**已经反过来**了 —— 那条 `tableEditing` 让位分支现在是主路径而非兜底，注释已改。

验证：6 个模块 curl 200、eslint 0 错误（`ContextMenuAutoClose.vue` 因"模板必须有根节点"改写成
`.ts` 渲染函数组件）。**未做浏览器验证**，交付时列了需老板手点的链路。文档同步到 v5（§9.5）。

## 回归修复：点单元格不出现选中蓝框

**现象**：表格编辑态下点单元格，选区框（`bg-primary/10` 底 + `border-primary` 活动格框）不出现。

**根因**：上一条修复（去掉 `stopPropagation`）的**直接副作用**。
`TableElement` 的 root 上有 `@pointerdown="onRootPointerDown"`，它原本无条件
`stopCellEditing()` + `setCellRange(null)`（语义是"点表格空白 = 清选区"）。
以前单元格自己 `stopPropagation`，root 收不到；去掉 stop 之后，点单元格的事件**冒泡到 root**，
于是执行顺序变成：

```
td 的 onCellPointerDown  → setCellRange(...)   ← 刚选中
  ↓ 冒泡
root 的 onRootPointerDown → setCellRange(null)  ← 当场抹掉
```

**教训（已写进 MEMORY.md）**：父容器的"清理型" handler 不能假设"事件到达我 = 落点在我身上"。
子元素不再 stop 之后，这个假设就崩了。

**修复**：`onRootPointerDown` 加落点判定 `if (e.target !== rootRef.value) return;` ——
只有落在 root 自身的留白/边框上才清空。行列把手与分隔线同样是 root 的子元素，一并豁免
（它们同样存在"`onColHandleDown` 设好整行选区、冒泡上来又被清掉"的同一个 bug）。
搜索确认 `setCellRange(null)` 全项目只有这一处。

验证：`TableElement.vue` curl 200、eslint 0 错误。dev server 已停。**未做浏览器验证**。

## 严重 BUG：两个表格互相关联（共享引用）

**现象**（老板报）：页面上拖两个表格，操作其中一个（如删除行），另一个跟着变。

**根因**：`createElement` 对载荷做的是**浅展开** `{...partial}`，而 `partial` 来自素材清单里
`mat-table.defaults` —— 那是**模块级常量**，`createTableDefaults(100, 50, 3, 5)` 在模块加载时
只调用了一次，`cells` / `colWidths` / `rowHeights` / `rowRoles` 数组全清单只有一份实例。
于是两个表格元素"两份外壳、一份内脏"。

**实测复现**（临时脚本 + esbuild 打包真实 `createTableDefaults`，跑完已删）：
```
修复前 cells 是否同一引用： true
  删表格1的一行后  表格1: 10 格（2 行 × 5 列） | 表格2: 10 格（2 行 × 5 列）
  → 表格2 是否被连累： 是（BUG 复现）
修复后 cells 是否同一引用： false
  → 表格2 是否被连累： 否（已修复）
深拷贝后仍与模板同引用的字段： 无
```

**连带发现（比原症状更狠）**：浅展开时 `before1.cells === defaults.cells` ——
删 A 表的行，改的**就是模块级模板本身**。所以之后拖出来的每个新表格都带着被污染的行数，
**且只有刷新页面才会恢复**。老板若见过"拖出来的新表格行数不对"，就是这个。

**修复**：
- `design.ts` 新增 `cloneElementPayload`（`structuredClone(toRaw(v))`，失败退回浅拷贝并 warn），
  `createElement` 改用它。一处收口，所有元素类型（表格 / 线条的 start·end·stroke）一并受益 ——
  线条其实也中招（两个线条共享端点对象，拖一个另一个跟着动），只是没人报。
- `materials.ts` 的 `defaults` 注释写明"这是单份模板，消费必须走 createElement"。
- `addElement` 补契约注释：入参必须自持数据。

**顺带核查**：`DEFAULT_CELL_PADDING` 是数字（原始值），无引用问题；
`setCellRange(null)` 全项目唯一；`pasteElement` / `copyElement` 已深拷贝。

验证：3 个模块 curl 200、eslint 0 错误、产物含 `structuredClone`。
**未做浏览器验证**（项目约定），但根因已用真实函数实测复现 + 确认修复。

## BUG：画布上一有两个表格，双击就改不了单元格文字

**现象**（老板报）：出现两个表格后，双击单元格无法进入文字编辑。

**根因**：第 3 层状态（`cellEditing`）是**全局单份 + 按坐标索引**的，不含"哪张表"这个信息。
`isEditingCell` / `editingKey` 只比坐标，没确认"本表是不是活动表" —— 于是编辑 A 表某格时，
**B 表同坐标的格子也渲染出一个 textarea**（两张 3×5 的表坐标必然重合）。

连锁反应：
1. 两个 textarea 各自 watch `editingKey` → 都去 `el.focus()`
2. 后聚焦的把先聚焦的顶掉 → 先被聚焦的那个触发 blur
3. `onCellBlur` 只比坐标（命中）→ `stopCellEditing()` → 刚开好的编辑当场关掉

净效果 = "双击没反应"。单表格时坐标唯一，所以只在 2 张表时才暴露。

**修复**：给三处补 `editing` 门禁（`editing = tableEditingId === element.id`）
- `isEditingCell(view)`：`if (!editing.value) return false;`
- `editingKey`：`if (!editing.value) return null;`（非活动表不写 draft、不抢焦点）
- `onCellBlur` / `onCellInput`：非活动表直接返回（后者是兜底，防止打字写进另一张表）

**审计结论**：全项目 `tableEditingId` / `cellRange` / `activeCell` / `cellEditing` 的消费点已逐一核对，
其余都带了 `element.id` 门禁（`selectionRect`、`activeRect`、行列把手高亮、单元格菜单上下文、
属性面板 `activeTable`），只有上述几处漏了。

验证：curl 200、eslint 0 错误、产物含 10 处 `editing.value` 门禁。**未做浏览器验证**。

## BUG：边框设置"改了不生效"（只能调宽，调细/去掉/改色全无反应）

**现象**（老板报）：改线型 / 线宽 / 颜色都不生效，只有点"应用到那条边"才生效；线宽还只能往宽了调。

**两个独立根因叠在一起**：

1. **交互心智**：`draft` 是面板内的局部状态，改它只改这份局部状态，只有点侧边按钮才写 store
   （"先配笔再应用"）。→ 改成**批改器**：面板显示的就是选区当前值，改任一项立刻重涂。
2. **真 bug：共享边只写了"自己那一半"**。渲染层每格只写自己四边，共享边交给
   `border-collapse` 合并，CSS 规则是**更宽者胜** —— 邻格那半边通常是**表格默认的 0.26mm**：
   - 调细到 0.1mm → 邻格 0.26 胜出 → 看着没反应
   - "去掉"（旧代码是**删掉属性**）→ 自己回落默认 0.26 → 线原样还在
   - 调粗到 1mm → 自己胜出 → 生效（所以只有"调宽"能用）

**修法**：新增 `model.ts` 的 `writeBorderEdge` —— 写一条边时**同时写进共享它的相邻格**（镜像到
对面边），两侧值恒等，CSS 没有可裁决的余地；合并格横跨多格时镜像到它跨过的每一格。
关边写**显式 `{style:'none', width:0}`**（删属性只是回落默认）。目标集合取**"可见的边"**，
不是"选区内所有格的所有边"（否则改外框线颜色会把已清掉的内部线复活）。
侧边按钮改为选区外缘语义、激活态读 `ownBorderEdge`；删除死代码 `resolveBorderEdge` / `resolveCellBorders`。

**实测复现**（临时脚本 + esbuild 打包真实 model.ts，脚本内复刻 CSS 裁决规则，跑完已删）：
```
旧写法 调细到 0.1mm → 该线实际线宽 0.26mm（症状复现）
新写法 调细到 0.1mm → 该线实际线宽 0.1mm
旧写法 删属性     → 线还在
新写法 显式 none  → 线消失
不变式 (r,c).bottom ≡ (r+1,c).top：不一致处数 0（横/竖两个方向均为 0）
合并格横跨 3 列时，上方 3 格的 bottom 全部被镜像
外框线后改色：外缘变色、内部线未被复活
```

连带修正文档三处已过时的表述（§3.B-7 / §6.2-5 / §8 与 §9.3-2）："交给 CSS 裁决"不完整 ——

## 22:50 插入列改为"表格总宽不变"（文档 v7）

老板要求："使用左侧右侧插入列时，表格的宽度会变，给他改成表格总宽度不变的，在内部变"。

**根因**：`insertCol` 里 `el.colWidths.splice(a, 0, borrowSize(...))` —— 新列从表格**外面长出来**，
`syncTableGeometry` 又把 `el.width` 回算成 `Σ colWidths`，元素框跟着一起宽。

**改法**（只动 `model.ts` 两个函数，调用点没变）：
1. `insertCol`：先取原总宽 `total = Σ colWidths`，把新列按**相邻列宽**挂进去（`borrowSize` 原语义：
   插最左借右邻、末尾借左邻），再整组等比缩回 `total`。`Σ ≡ width` 因此严格保持。
2. 新增 `fitTracks(sizes, target)`（放在 `scaleTracks` 之后）：等比缩放 + **`MIN_TRACK` 下限兜底** ——
   缩放后跌破 2mm 的项抬回下限，抬出来的量从"还有富余的列"里按富余比例扣回，末尾把舍入残差
   贴到最宽的项上。纯 `scaleTracks` 不够用：`[98,2]` 这类贴边表插一列会得到 1.96mm 的缝。

**刻意没做**（避免范围蔓延，已在回复里问老板）：
- 插入**行**仍然让表格变高（宽度是版面约束、高度是内容量）。
- 删除列仍然让表格变窄（删列往往就是想腾宽度）。要改的话都是一行 `fitTracks`。
- 插入列后**选区不平移**：在 A 列"左侧插入"后选区仍指坐标 c1，而 c1 现在是新列，视觉上像"选区跳到新列"。
  这是既有行为，不是本次引入 —— 一并报给老板让他定。

**验证**：临时脚本 `node .tmp-insert-col-check.ts`（Node 22 直接跑真 `model.ts`，不用 esbuild，跑完已删），
29 条断言全绿：等宽 3→4 列得 `[25,25,25,25]` 总宽 100 不变；插最左/追加末尾/连插 20 列（180→23 列）总宽严格不变；
`Σ colWidths ≡ width` 在所有分支成立；无列低于 `MIN_TRACK`；`[70,30]` 保持宽窄关系；`[98,2]`→`[49,49,2]`；
跨线合并格 `colspan` 正确 +1 且新格标 `covered`。eslint 0 错误、model.ts curl 200、dev server（5199）已停。

## 23:00 整表批量改行高（文档 v8）

老板报："没有办法调整整体表格的行高，只能一行一行的改，怎么统一一下修改所有的行高"。

**根因是两层叠加**：
1. 表格编辑态下元素级面板被**替换**成单元格面板（需求 ④ 的粒度切换），"位置 & 尺寸"里的

2. 单元格面板的行高输入框带 `v-if="rowHeight !== null"` —— 只有**选中整行/整列**才渲染，
   随手点一格时面板里连行高都找不到，必须先点行把手 → 改 → 再点下一行把手。

**改法**：单元格面板**最前面**新增「整表行高 / 列宽」项（`value="table-size"`，不依赖选区、常驻），
两个字段：每行行高、每列列宽。写入走 `model.ts` 新增的 `setAllTracks(el, axis, value)`。
- 显示值取现有尺寸的**平均**（全等时就是那个值，参差时给代表值，改一次即拉平）；
  说明文字点明"当前不一致时显示平均值"，并提示"要总尺寸不变、行间平分用右键的平均分布"。
- `setAllTracks` 显式挡 `null` / `undefined` / `NaN` —— 输入框清空是编辑中间态，
  不挡的话 `Math.max(MIN_TRACK, 0)` 会把全表行高夹成 2mm。
- 尺寸模式一并回落 `fixed`。

**至此"改轨道尺寸"三个语义靠「总尺寸变不变」划清**（已写进 MEMORY.md 与文档 §9.9 的对照表）：
拖分隔线（相邻让位、总尺寸不动）/ 右键平均分布（选区内等分现有总长）/ 整表统一（= 数量 × value）。
另有第三条路径：非编辑态下元素级"高度"或拖缩放手柄 → `updateElement` 对表格走 `scaleTracks` 等比缩放。

**验证**：临时脚本 17 条断言全绿（5 行统一 8mm → 总高 40、总宽不动；`[4,12,6,8]` 一次拉平；
