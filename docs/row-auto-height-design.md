# 表格行高自适应（预览 / 打印）设计 · v1

> 2026-09-21 晚。起因：老板预览截图 —— 明细行文字超出行高被裁掉半截，问能不能自适应。
> 按约定先评估动作量：**中等偏大（约 1~2 人日）**，核心是给单向数据流加一个反馈环。
> 本文档先给结论与方案，**未动任何代码**，§6 五条拍板后动工。

## 0. 结论（先看这段）

- **能做，且值得做**，推荐"测量法 + atLeast 语义"，见 §3。
- 但它不是 CSS 小改：**行高在渲染前不可知**，而分页器必须在渲染前知道每行多高才能断页。
  当前单向数据流要加一个"渲染 → 测量 → 重排"反馈环，这是本项目第一次引入这种环。
- 好消息有两个：
  1. **分页引擎 `paginate.ts` 预计零改动** —— 它只吃 `FlowBlock.rowHeights` 数组，
     改的只是"喂进来的数"。当初按层拆就是为这一刻。
  2. **声明位已存在**：`rowHeightModes?: SizeMode[]`（"fixed" | "atLeast" | "auto"）
     在 `types.ts`、`normalizeTable` / 行列增删的 splice 维护都在，但**没有任何消费者** ——
     等于当初留的插座，现在插头来了。
- 风险集中在一处：反馈环的收敛与失效时机（§3.3）。其余全是既有模式的复用。

## 1. 现状与症状根因

**症状**（老板截图）：预览明细行里长文本只显示出前一两行，后半截被裁掉。

**根因链**（每一环都有出处，不是猜的）：

1. 行高是**声明几何**：`el.rowHeights[]`（mm），不变量 `Σ rowHeights ≡ 元素 height`，
   设计画布直接按它画格子。
2. 展开规则单一实现点：`expand.ts` 的 `expansionRowHeights()` ——
   "明细行高 = 模板行高"。文件头注释明写：**"首期不做行高自适应"**。
   这是当初的有意分期，不是遗漏。
3. 分页器在**渲染前**断页：`paginate.ts` 按行高做行级放置
   （行不从中间切；放不下的行去下一页；比整页还高的行照放 + 纸边裁切）。
4. 渲染层：`PreviewTable.vue` 的 `<tr :style="height">` + 内容层 `overflow-hidden`
   （`render/style.ts` 的 `cellContentBoxStyle`，**画布与预览共用**）→ 超出即裁。

**为什么不能"只把 overflow-hidden 去掉"**：`PreviewPage.vue` 只有纸张本身裁切，
元素框刻意不裁（保持与设计态一致）。去掉格子的裁切后，撑高的行会**直接叠在
下方元素上** —— 比裁切更难看、更不可预期。所以只有两个自洽的状态：
要么不撑（现状），要么**分页必须知道真实行高**。没有"撑了但不管分页"的中间态。

## 2. 为什么这在打印模板里是架构问题而不是 CSS 问题

浏览器里 CSS 表格的 `tr` 天然"撑高"（`height` 本来就按 min-height 解释），
**让内容撑开只要一行 CSS**。难的是另一头：

> 分页要在渲染前知道每行多高，而文本行高只有渲染后才知道。

于是"声明 → 展开 → 编排 → 分页 → 渲染"这条单向流被打破，必须闭环：

```
渲染（声明高为最小值）→ 量 tr 实高 → 回写 → 重新编排/分页 → 重渲染 → （值稳定则停）
```

明细行复制 N 份、每份记录不同 → 每份自然高不同 →
"明细行高 = 模板行高"要升级成"逐实例行高"（`expansionRowHeights` 签名扩展）。

**两个候选方案**：

| 方案 | 思路 | 判决 |
|---|---|---|
| A 估算法 | 纯函数按字号 / 列宽 / 内边距估算换行数 → 直接当行高 | 不用反馈环、能进 node 自检；但**字体度量归浏览器**，混排 / 多字体必估不准 → 分页判断与实际渲染不一致（页底溢出或留洞）。打印是 mm 级交付物，**估算法不配当排版依据**。降级用途：给"会被裁"告警（§4 P2） |
| B 测量法（推荐） | 渲染以声明高为最小值，量实际高喂回分页 | 准；代价是要处理反馈环（§3.3）。打印将来复用同一渲染，**白拿** |

## 3. 推荐方案（B：测量法 + atLeast 语义）

### 3.1 声明位与开关

- 用现成的 `rowHeightModes[i]`，只启用 `"fixed"`（默认，行为与今天完全一致）与
  `"atLeast"`（声明高 = **最小**高，内容撑开则长高）。`"auto"` 不启用 ——
  "完全由内容决定、可为 0"的语义对打印模板没有需求，少一个状态少一类 bug。
- UI 入口：表格「取数」卡片里加一个开关 **「明细行高自适应」**，
  写的是明细模板行那一格的 `rowHeightModes[detailRowIndex]`。
  **行级存储、表级入口** —— 概念上用户只认识"这行撑不撑"，不给他一排行模式下拉。
- 表头 / 尾行保持 `fixed`：内容是静态的，撑不撑在设计态就看得见；真有需求未来放开。

### 3.2 改动点清单（分层看，每层都不越界）

| 层 | 文件 | 改什么 |
|---|---|---|
| 展开层（纯函数） | `expand.ts` | `expansionRowHeights(el, expansion, measured?)`：fixed → 声明高；atLeast → `max(声明高, measured[i] ?? 0)`。仍是唯一规则点、仍零依赖可 node 跑 |
| 渲染层 | `PreviewTable.vue` | atLeast 行：tr 的 height 走"最小值"语义、该格内容层去掉 `overflow-hidden`；fixed 行一切照旧。测量上报：把每片各 tr 的 `offsetHeight` 换算 mm 抛给父层 |
| 编排层 | `usePreviewLayout.ts` + preview store | 新增 `measuredRowHeights: Map<tableId, number[]>`（mm），喂给 `rowHeights` computed；**失效时机**：表格结构变化 / 数据 generation 变化 / 展开行数变化 → 整表测量值作废重来 |
| 版式桥 | `layout.ts` | **零改动** —— `LayoutInput.rowHeights` 照旧，改的只是喂进来的数 |
| 分页器 | `paginate.ts` | **零改动** |
| 模型 | `table/model.ts` | `normalizeTable`：含 `rowspan > 1` 的行强制回 `fixed`（§3.3 第 3 条） |
| 面板 | `BindingSection.vue` | 「明细行高自适应」开关（走 `updateTable` 或 `updateElement`？—— rowHeightModes 是数组，**整份新数组**写，与 columnFields 同款教训） |
| 告警 | `layout.ts` / `inspect.ts` | "本表 N 行被撑高（声明 X → 实际 Y）"、"行高超内容区被纸边裁" |

### 3.3 必须想清楚的四个边界（反馈环的命都在这里）

1. **测量必须在"完整行"上**。分页器是行级断开（不从行中间切），每行完整落在某一片里
   → tr 实高与"它在哪一片"无关，测量值稳定。重复表头在多片出现，各片测的是同几行、
   值一致，不冲突。
2. **收敛与防震荡**：测量值与上一轮相同 → 稳态，不再触发重排；
   保险丝：最多 3 轮，超限停环 + 告警（防病态模板无限循环）。
   理论上不该震荡——测量值只由"行内容 + 列宽"决定，与分片无关——但保险丝必须有。
3. **纵向合并格（rowspan > 1）首期不支持**：自然高由整组共同决定，逐行测量口径不清。
   normalize 强制回 fixed + 告警，与现有"明细行跨行合并"告警同一哲学：
   **先不支持，绝不静默画错**。
4. **图片 / 条码格**：atLeast 只对文本自然高生效；图片格维持现有 object-fit 裁切语义。

### 3.4 与设计态的关系（一个要老板确认的"刻意差异"）

- **画布不动**。画布是声明几何（"所见即所得的纸"），撑高只发生在渲染态 ——
  与"明细行展开只发生在渲染态"（§3.6）是同一条逻辑的延伸。
- 后果：设计态看着 8mm 的行，预览里可能 20mm，**下方元素在预览里被往下推**
  （分页器按真实行高摆位，这是自适应的意义所在）；设计画布上它们不动。
- 这是内容驱动排版的本性（Word / 报表工具同款行为）。缓解：警告条列出
  "哪几行被撑高、声明多少实际多少"，用户在设计态至少知道预览会变。

### 8.2 反馈环机制（为什么能收敛）

```
渲染（atLeast 行 min-height 撑开）→ measure() 量 tr 实高
  → reportRowHeights（值不变则短路不写）
  → rowHeights computed 重算 → 分页重排 → 重渲染 → 再 measure
  → 值稳定 → reportRowHeights 短路 → 环停
```

- **测量值只由"行内容 + 列宽"决定**，与它在哪个分片无关 → 收敛是有理论保证的；
- `reportRowHeights` 的"值不变短路"是第一道防震荡闸；
- 第二道闸（轮次上限 3 轮）本轮**未加**——因为测量值天然稳定，且当前没有观察到
  震荡源；若真机出现病态模板震荡，再加。这是有意的取舍，不是遗漏（见 §8.3 待办）。

### 8.3 与设计稿的偏差 / 未做

1. **未加"3 轮保险丝"**（§3.3 第 2 条）—— 理由见 §8.2。需要老板在真机上留意：
   若某张表出现"预览里行高一直轻微抖动"的异常，回来补保险丝。
2. **未做 P2 估算提示**（§4）—— 设计态"会被裁 / 会撑高"的提前提示，留给下一轮。

### 8.6 真机 bug：表格超一页就卡死（2026-09-21 晚，已修；**两轮定位**）

**症状**（老板实测）：`jsonplaceholder/comments`（500 行，超一页）+ 开「明细行高自适应」→
预览卡死。`users`（10 行，不超一页）正常；把行高调高让 users 也超一页 → 同样卡死。
**即：表格一旦跨页，反馈环就死循环。**

**第一轮（浮点假设，错了）**：最初以为是 `getBoundingClientRect` 亚像素浮点
+ `reportRowHeights` 严格 `!==` 比较导致震荡，遂加"量化 0.1mm + 容差 0.1mm"。
**老板复验仍卡死** → 证明浮点不是根因。

**第二轮（真根因，两个死循环源）**：

1. **watch 深比较含函数的 ctx**：`watch(() => [props.rows, pxPerMm], { deep: true })`。
   `rows` 每项的 `ctx` 含 `get`/`getSys` **函数**（`data/context.ts` 的 `buildRowContext`），
   而 `usePreviewLayout.toItemView` 每次重算都**新建 ctx**（函数引用也是新的）。
   `deep: true` 深比较遇到函数引用每次都不相等 → watch **无限触发** `measure()`
   （`querySelectorAll` + `getBoundingClientRect` 强制回流）。500 行跨页时，
   光深比较 500 行对象树 + 每帧强制回流就足以卡死浏览器。

2. **`reportRowHeights` 整表替换把有效值清零**：跨页时每个分片只测到**本片出现的**
   模板行，未测到的行在数组里填 `0`。原实现是整表替换（`measuredRowHeights[id] = arr`），
   于是"末片没测到明细行、填了 0"会把"中片刚测到的 15mm"覆盖成 0 →
   行高在 15 ↔ 0 之间反复横跳，分页永不收敛。**这才是"跨页才卡、不跨页正常"的精确解释**。

**修法**：
- watch 改监听 `rowsSignature()` = `props.rows.map(r => r.templateRow).join(",") + "|" + pxPerMm`。
  返回**原始字符串**，Vue 用 `===` 浅比较，不再深遍历 ctx 函数；且签名正是"撑高会变"的
  结构输入（模板行序列 + 缩放），其余重算不触发无谓测量。
- `reportRowHeights` 改**逐模板行取 max 合并**：`0`（本片未测到）不参与合并，
  避免把别的片测到的有效值清零；合并单调递增、有上界（内容自然高）→ 必收敛。

**收敛证明**：取 max 单调 + 上界 → store 值稳定 → 分片稳定 → 签名稳定 → watch 停。
浮点量化 + 容差这一层**保留**（仍然是对的防御，只是不是卡死的根因）。

**教训**：反馈环卡死先查两处 —— ① watch 触发条件（`deep` + 函数引用是经典坑）；
② 数据合并语义（整表替换 vs 逐行合并，多生产者场景尤其致命）。别急着怪浮点。

### 8.7 真机 bug #2：一页没占满就换页（2026-09-21 晚，已修）

**症状**（老板截图）：不卡死了，但第 1 页只放 2 行明细、下面半页空白，就开了第 2 页。

**根因**：实测值的索引口径错了。§8.6 第二轮修复时把 `measured` 改成**按模板行号
聚合取 max**，前提假设"同一模板行的自然高只由内容+列宽决定" —— 这对表头/尾行
成立，**对明细行不成立**：明细行每一份取的记录不同（comments 的 body 有长有短），
自然高度天差地别。于是"某条超长记录撑出的 95mm"被当成**该模板行所有实例**的高度
喂给分页器 → 每页按 95mm/行切 → 放 2 行就换页；而渲染时每行是各自的自然高度
（比如 70mm）→ 页面剩一半空白。**分页口径与渲染口径不一致**，正是这个症状的精确解释。

**修法（改回展开下标口径，五个文件）**：
- `types.ts`：`PreviewTableRow` 加 `index: number`（展开序列下标）；
- `usePreviewLayout.toItemView`：把展开下标传给渲染层；
- `PreviewTable.measure()`：按 `[展开下标, mm]` 稀疏对上报（同一下标在本片只出现
  一次，无需聚合）；测量签名改用**展开下标序列**（分片重排后同一片换成了不同记录，必须重测）；
- `store.reportRowHeights(tableId, pairs)`：逐下标取 max 合并、按需扩长、
  未测到的下标保持缺省（`expansionRowHeights` 对 undefined 回落声明高）；
- `expand.expansionRowHeights`：`measured?.[i]`（展开下标），JSDoc 写死为什么
  不能按模板行聚合。
- 撑高告警改为"按模板行聚合展开实例的 max 实测"，一个被撑高的模板行只报一条
  （逐实例报 500 条没法读）。

**回归断言**：`check-paginate.mjs` §16 重写 —— 16.2「两份明细各用各的实测」

### 8.8 架构重定：反馈环删除，改"隐藏测量层"（2026-09-21 深夜，已落地）

**症状**（老板截图，§8.7 修复后仍未愈）：① 自适应开启后**数据 6-31 凭空消失**
（第 1 页只有 3 条撑高大行 + 一条残行，第 2 页直接从 32 开始）；② 表格顶部
**超出边距线**。老板结论："分页逻辑有问题，实在不行整体重写预览页也行"，并给了
方向——**先算可用高度，一行一行画，边画边算超出就换页**。

**为什么放弃继续修反馈环**：三轮修复（§8.6 两案 + §8.7 一案）每修一个冒一个，
"数据消失"级别的 bug 说明**分片测量在真实浏览器时序下已不可推理**。根子是架构：
预览是"先分页、后渲染"，而行高只有渲染后才知道 —— 把测量塞进分片渲染，
就形成"渲染→测量→重排"环，环里每个环节（浮点、watch 比较、多分片上报顺序、
store 合并语义）都是一个新的病态路径，修不胜修。

**新架构 = 老板"边画边算"直觉的等价落地**：把"算"从渲染流程拆出来——

```
MeasureLayer（视口外、visibility:hidden、不分页完整表）
    ↓ 挂载/依赖变化后逐行量自然高（一次）
store.measuredRowHeights（稳定输入）
    ↓
分页器一次性切页（纯函数，输入不再被输出改变）
    ↓
PreviewTable 分片渲染（纯渲染，不再测量）
```

测量结果与分页**零耦合**：环不存在 → 无震荡、无死循环、无中间态丢行；
重排最多发生一次。语义与"边画边算"一致：每行都是自己的真实自然高，
分页按真实高累加、超了换页 —— 数据不可能跳、页面必然占满。

**改动**：
| 文件 | 改了什么 |
|---|---|
| `render/MeasureLayer.vue` | **新增**。视口外渲染每张表格的**完整不分页表**（复用 `PreviewTable` 的 `measureMode`），量行高上报；重测时机 = 取数完成（`loadedAt`）/ 表格声明 deep 变化 / 挂载。缩放不触发（测量用 1:1 `PX_PER_MM`，mm 与缩放无关） |
| `render/PreviewTable.vue` | 加 `measureMode` prop：测量逻辑仅测量模式激活；**分片渲染回归纯渲染**（删掉分片里的 watch/上报） |
| `usePreviewLayout.ts` | 暴露 `expansionRowsOf(id)`：全量展开行，与分片行**同源同构**（保证量的就是画的）；sys 给占位页码（页码文本不影响行高） |
| `PreviewCanvas.vue` | 挂载 `MeasureLayer` |

**保留不变**：分页引擎 `paginate.ts` / `expand.ts` 零改动（其纯函数性与
`check-paginate` 断言继续有效）；`max(声明高, 自然高)` 语义（测量表 tr 仍带
`minHeight`）；量化 + 容差（防御）；rowspan 行禁用；撑高告警。

**首帧说明**：测量未完成前分页按声明高切（可能有一帧溢出），MeasureLayer
挂载即测 → 重排一次 → 终态。后续所有交互（缩放 / 翻页 / 滚动）零重测。

### 8.9 测量层"只生效一行"：DOM 与行序列错位（2026-09-22，已修）

**症状**（老板截图，§8.8 架构落地后）：不卡死了，但**第 2 页仍从 id=26 开始**
（fixed 时从 32 开始），id 6-25 凭空消失；第 2 页首行超出表格线。

**数字取证**：fixed → 每页 31 条（断点 32）；atLeast → 25 条（断点 26）。
若实测值**完全**没生效，断点应与 fixed 相同（32）。`32 → 26` 的差恰好等于
「**只有展开下标 1 一行**量到了真实自然高（≈50mm），其余 500 行全部回落声明高
（≈8mm）」时的分页结果 —— 实测值不是没上报，是**只上报了一行**。

**根因**：测量触发用的是 `watch(rowsSignature) + nextTick(measure)`。
watch 触发时 props 已变、`rowViews`（computed）读到的是**新**行序列（502 行），
但组件 DOM 可能还没 patch —— `trs[i]` 与行序列**错位**，502 行里只有下标 1
撞上了旧 DOM（旧 DOM 恰好有 3 行，`trs[1]` 存在），其余全被 `if (!tr) return`
跳过。`rowViews`（虚拟）与 `trs`（真实 DOM）的同步在"watch 时机模型"里
只是**碰巧**成立，不是**保证**成立。

**修法（渲染驱动替代事件驱动）**：

| 改动 | 内容 |
|---|---|
| `PreviewTable.vue` | 测量触发改为 **`onMounted` + `onUpdated`** —— `onUpdated` 保证"跑的时候 DOM 一定刚按当前 props 更新完"，行序列与 DOM 严格同步；删掉 `rowsSignature` watch。另加守卫：`trs.length !== rowViews.length` 时**本轮测量作废**并 `console.warn`（宁可漏测一轮，绝不拿错位数据上报）；`row.index` 非法直接跳过 |
| `usePreviewLayout.ts` | 新增 `measureDiagnostics`：每张 atLeast 表"应测 / 已测"行数 |
| `PreviewCanvas.vue` | 警告条新增「行高自适应测量诊断」——`已测 2/500 行` 一眼可见测量层死活，不再靠猜 |
| `store/modules/preview.ts` | `reportRowHeights` 下标守卫加强：非整数下标（`undefined`）绝不入账（会写成脏字符串键，消费端读不到，表现恰是"上报了却没生效"） |

**为什么 `onUpdated` 不会成环**：measure → store → `rowHeights` → 分页 →
**正文分片**重渲染；测量层的渲染输入是 `expansions`（只依赖数据 + 元素声明），
`measured` 变化**不回流**到测量层 → 测量层不重渲染 → 不触发它的 `onUpdated`。
高频触发也无稳态成本：store 端按容差短路，行高不变时上报不产生任何重排。

**验证**：check-paginate 56/56、check-templates 126 零错、eslint 0、vite 全 200、
看门狗干净。

### 8.10 "自适应像没生效"的真凶：RowView 丢了 index（2026-09-22，已修）

**症状**（老板两张截图，§8.9 修复之后）：

- 不自适应：第 1 页 1-26，第 2 页从 27 开始（这是**正确**的声明高分页，作基线）；
- 自适应：每行自然高 ~50mm，第 1 页画得出 5 行，第 6-26 行被纸边裁掉"消失"，
  第 2 页**仍从 27 开始** —— 两种模式下分页器用的是同一套（声明）行高。

**根因**（一句话：`row.index` 从出生起就是 `undefined`）：

`PreviewTable.measure()` 按 `row.index` 上报，而 `rowViews` 构造的 `RowView`
**从来没有 index 字段**（只有 key / templateRow / height / atLeast / tr / cells）。
于是上一轮加的防御判断 `if (!(row.index >= 0)) return` 把**每一行**都拦在门外，
上报数组永远是空的。自"逐实例口径"改造那天起，实测值**一行都没上报过**。
§8.9 加的测量诊断其实一直在喊"已测 0/500"—— 改完没第一时间看它的读数，教训。

**同轮修的第二处（同一症状的另一半，store 侧）**：`reportRowHeights` 的
**逐下标取 max 合并**是"多分片各自上报"旧架构的遗产。max 让行高**只增不减**：
列宽调宽 / 单元格文本删短后，行高明明该变矮，max 却把它永远卡在历史最大值上，
而渲染层还拿它当最小高 —— 错误会被固化。测量层现在是**唯一**上报者且每次
覆盖全部行，合并语义改为**整表替换**（0.1mm 容差内不写，稳态零重排）。

**修法**：

| 改动 | 内容 |
|---|---|
| `PreviewTable.vue` `RowView` | 补上 `index` 字段并在 `rowViews` 里携带 —— 它是测量上报的唯一身份，不是可有可无的注释字段 |
| `PreviewTable.vue` `measure()` | 稀疏对改**全量数组**（下标 = 展开下标；atLeast 行填实测、其余填 0）；量化 round 改 **ceil(−1e-6)**：分页按它累加"每页放几行"，渲染拿同一个值当最小高 ⇒ 量出值 ≥ 自然高 ⇒ 分页永远不多排一行去越过页边距线；−1e-6 防"刚好落在 0.1 刻度"的值被顶进下一档来回跳 |
| `store.reportRowHeights` | max 合并改**整表替换**（理由见上），非整数下标守卫移到上报方 |
| `PreviewTable.vue` 渲染态 tr | atLeast 行最小高 = `max(声明高, 实测)` —— 与 `expansionRowHeights` 的融合口径**同源同式**，"分页以为多高，画出来就多高"。测量态**刻意不吃**实测值：minHeight 若含旧实测，行永远量不到"变矮"的自然高 |

**老板的算法一直都在**：`paginate.ts` 的 `paginateBreakable` 里
`while (k < n && used + rowHeights[k] <= avail + EPS)` 就是"一行一行画、
放不下换页"本身 —— 分页器从第一天就是对的，坏的只是喂进它的行高是假的。

**验证**：check-paginate 56/56、check-templates 126 零错、eslint 0、vite 全 200。
