## 0. 先说结论

表格在这个项目里**不是一个"元素样式"问题，而是一套嵌套的二级编辑器**。

现在的元素体系是「一个元素 = 一个平铺字段对象 + 一个渲染组件」，表格是唯一一个**内部还有结构**的元素：它有行列、有网格、有单元格级属性、有跨格合并（合并后网格拓扑本身会变）。这意味着三件事必须新增，而不是"往 `TableElement` 上再加几个字段"：

1. **单元格矩阵要成为一等数据模型**（`rows: number` 撑不住合并与逐格样式）。
2. **要有"表格内编辑态"**——元素/单元格/单元格内文本，三层嵌套的选中与编辑，且必须与现有元素拖拽手势互斥（否则点单元格会变成拖整张表）。
3. **右键菜单与属性面板要按"当前选中层级"分流**——现在是按 `element.type` 分流的，表格需要第二个维度（表格体 / 单元格 / 行 / 列 / 选区）。

**定位已定**（v2）：这是**数据驱动的明细表**——行数终将由数据决定（单据明细：品名/规格/数量/单价/金额）。但数据绑定尚未开发，**第一期只实现静态排版交互**。因此在 §1.5 列了 6 条「数据表格反向约束第一期」的设计决定，**这些必须在第一期就做对**，否则接数据绑定时要返工。

## 1. 定位（已定）：数据驱动的明细表，第一期做静态排版

**结论**：这个表格是**数据驱动的明细表**，终局场景是单据/票据的明细区（品名 / 规格 / 数量 / 单价 / 金额），**行数由数据决定**。但数据绑定功能尚未开发，**第一期只实现静态排版交互**。

两条路线的差别（保留作背景，便于回看选择依据）：

| | A. 排版表格（静态） | B. 数据表格（驱动）← **终局** |
|---|---|---|
| 行数 | 设计时固定，用户手动增删 | 运行时按数据条数动态生成 |
| 单元格内容 | 用户输入的固定文本 | 字段绑定（`{品名}`）+ 固定文本混排 |
| 表格高度 | 等于各行高之和 | 随行数增长，跨页自动延续 |
| 参考对象 | Word / WPS 文字的表格 | 报表工具（FastReport）、标签软件（中琅/BarTender） |
| 复杂度 | 中 | 高（数据源、表达式、分页、合计） |

**策略：按 B 建模型，按 A 做交互。**

- **交互层第一期只做 A**：矩阵模型、选区、合并拆分、单元格样式、行高列宽——这些在 B 里要 100% 原样复用，先做不会被推翻。
- **模型层从第一期起就按 B 预留**：具体是 §1.5 那 6 条。**预留的成本是"现在多写几个字段"，不预留的代价是"将来重写几何逻辑 + 迁移存量表格数据"。**

这个顺序是对的。反过来（先按纯静态设计高度与行高分配，将来再补数据）会推倒重来，因为**静态表格的几何假设和数据表格是直接冲突的**（见 §1.5 约束 1）。

## 1.5 数据表格对第一期的 6 条反向约束（**重要：第一期必须做对**）

这几条的意思是"虽然第一期不做数据绑定，但设计时必须按数据绑定来"。前 3 条是**结构性决定**，不做将来必返工；第 4、5 条是"不要做错方向"；第 6 条是排期依赖。

### 约束 1（最关键）：元素 `height` 不是权威值，行高之和才是

现在 `TableElement` 撑满元素框（`h-full w-full`），即**元素框的 width/height 是权威**，行高列宽只是"内部分配"。数据表格下这条必然翻转——行数由数据决定，高度只能由内容推导。所以第一期就确立这套几何：

```
元素 width  ≡ Σ colWidths        （强约束）
元素 height ≡ Σ rowHeights       （静态期强约束；数据版降级为"设计时快照"）
```

派生出四条明确的交互语义：

- **拖元素缩放手柄** → 等比缩放所有 `colWidths` / `rowHeights`（框变了，比例不变）
- **拖行/列分隔线** → 只改**相邻**两行/两列，总和不变 → **元素框不动**
- **属性面板改宽高** → 同"拖元素手柄"
- **插入列** → 列数 +1、宽度在**内部重新分配**，`Σ colWidths` 不变 → **元素框不动**
  （插入**行**不适用：宽度是版面约束，高度是内容量 —— 明细表插一行就该变高。见 §9.8）

**为什么必须现在定**：若第一期写成"行高按百分比分配、靠 CSS 拉伸填满框"，接数据时行数一变，百分比分配逻辑整个失效，几何层要重写。

### 约束 2：单元格内容从一开始就是"可含占位符的文本"，不做转义与校验

标签/报表软件的通用做法是：单元格内容是**数据对象的序列**（固定文本 + 字段 + 系统变量 + 序列号）。第一期只存纯文本，但结构上留口子：

```ts
content: { type: "text"; value: string }   // value 允许含 {品名} 这类占位符，设计态原样显示
```

- **不要加"占位符校验 / 转义 / 高亮"逻辑**——`{品名}` 在设计态就当普通字符渲染（将来再做设计态高亮）。
- **不要把"固定文本"和"绑定字段"设计成两种数据结构。** 这是最容易犯的错：一旦拆成两个字段，混排场景（"单价：{单价} 元"）就要拼接，越往后越难拆。

### 约束 3：行必须有"角色"字段：表头行 / 明细模板行 / 合计行

第一期看着毫无用处（用户手动加的行就是普通行），但**成本是一个可选字段，不做的代价是将来要在存量表格上做行角色推断**。数据版必须靠行角色区分两件事：

- **哪一行是明细模板** → 数据按它复制 N 份（`detailRowIndex`）
- **哪些行每页重复** → 表头行（`headerRows`，同时服务 P1 的"跨页表头重复"）

第一期就落 `headerRows?: number`，并把行角色存下来（默认全部"普通行"）。

### 约束 4：行高列宽的"模式"要进模型，不能只有数值

```ts
rowHeights: number[];                                  // 数值（mm）
rowHeightModes?: ("fixed" | "atLeast" | "auto")[];     // 每行的模式
colWidthModes?: ("fixed" | "atLeast" | "auto")[];
```

- 静态期至少要有 `fixed`（拖多少就多少）和 `atLeast`（拖出的值是最小值，内容多了行会涨）。**Word 的默认手感是后者**——用户拖行高时的预期通常是"至少这么高"。
- 数据版的明细行几乎必然是 `auto`（内容长度不可控）。
- 注意 `atLeast` / `auto` 会**打破约束 1 的强等式**（行被内容撑高 → 实际高度 > 设定值）。处理方式：静态期把元素 `height` 视为"设定值"，实际渲染高度取 `max(设定值, 内容所需)`，并明确"框要不要跟着涨"（**建议涨，且回写元素 height**，否则内容会溢出框外）。

### 约束 5：溢出策略第一期定，**不要做"溢出到相邻单元格"**

内容溢出三选一：`自动换行` / `缩小字号适应` / `裁切`。**建议默认"自动换行 + 撑高行"**（配合 `atLeast`）。

明确排除 Word 那种"不换行、文字直接溢到相邻空格"的"适应文字"模式：**数据一长就串到隔壁列**，静态期看着能用，数据版必崩。第一期就别做，免得上瘾。

### 约束 6：分页是数据表格的前置依赖，需要确认排期

数据驱动的明细表**必然跨页**（100 条明细不可能塞进一页），跨页需要两个能力：`允许跨页断行` + `表头行每页重复`。

但项目现在**连多页渲染器都没有**（导出/打印仍是占位）。所以这条不是表格功能本身的问题，而是**依赖项**：

> **待确认：多页渲染 / 打印导出排在哪个阶段？** 它卡着数据表格的最后一公里，也卡着 P1 的跨页表头重复。

## 2. 现状盘点（基于代码事实）

### 2.1 已经有的

| 能力 | 现状 |
|---|---|
| 表格元素 | 素材台可拖出（默认 3 行 × 5 列 / 100×50mm），画布可选中、移动、缩放、旋转、锁定、复制粘贴 |

| 右键菜单 | 只有两项：「增加一行」「增加一列」（点了就把 `rows/cols` 各 +1，加在末尾，无法指定位置） |
| 属性面板 | 「表格设置」一组：行数、列数、边框颜色、边框宽度、单元格内边距（**全表生效，无单元格概念**） |
| 配置驱动 | 菜单是 `context-menu-config.ts` 声明式配置，面板是 `element-property-config.ts` 声明式配置，都按 `element.type` 取 |

代码位置：
- 渲染 `designPanel/components/elements/TableElement.vue`（30 行）
- 模型 `types.ts` → `TableElement { rows, cols, cellStyle? }`
- 菜单 `elements/context-menu-config.ts` / `ElementContextMenu.vue`
- 面板 `setting/element-property-config.ts` / `ElementProperties.vue`

### 2.2 三个架构级缺口

**缺口一：数据模型装不下单元格。**
`TableElement` 现在只有 `rows/cols/cellStyle` 三个字段，`cellStyle` 还是全表一份。要支持"每个单元格自己的文本、边框、背景"，必须有二维（或扁平的 `r,c` 键）单元格数组；要支持合并，还得存 `colspan/rowspan`，并且**合并会改变"逻辑格子 → 物理格子"的映射**（第 2 行第 3 列到底是哪一个格？取决于第 1 行有没有跨下来）。这是全部后续功能的基石。

另外一个实现层的坑：现有写入口 `store.updateElement(id, patch)` 是**浅 `Object.assign`**，属性面板的 `setField` 用点路径构造 patch。二维数组没法用点路径表达，单元格写入需要独立的 action（如 `updateCells(elId, cells, patch)`），并且要保证整包替换而非逐格赋值（否则高频拖动会触发 N 次响应式更新）。

**缺口二：没有"表格内编辑态"，且现有手势会与之冲突。**
现有 `editingId` 是**元素级**内联编辑（一次一个文本元素）。表格需要三层：

```
第 1 层  元素选中      ← 已有：拖整张表、缩放、旋转、锁定
第 2 层  单元格选中/活动格  ← 新增：选区、合并拆分、单元格样式、行高列宽
第 3 层  单元格内文本编辑   ← 新增：进格编辑，复用 TextElement 的 textarea 范式
```

冲突点很具体：`ElementWrapper.onPointerDown` 在元素上按下就 `selectElement` + `mode = "move"` + 起拖拽手势。用户点某个单元格（第 2 层）会先冒泡到这层，**变成拖动整张表**。必须引入"表格进入编辑态"的概念并让第 1 层手势让位。

**缺口三：菜单与属性面板只有"类型"这一个维度。**
`getElementContextMenuConfig(type)`、`ELEMENT_PROPERTY_CONFIG[type]` 都是按类型取。表格的菜单要按**上下文**取（表格体右键 ≠ 单元格右键 ≠ 行头右键 ≠ 选中区域右键，你在需求 4 里已经点了这条），面板同理。配置表的 key 要从 `ElementType` 升级成 `ElementType + 选中上下文`，这是"需求 4 其实是架构需求"的意思。

## 3. 需求清单

### 3.A 你提的 6 条（逐条确认与展开）

**① 单个单元格能设置文本、边框、背景色、边框样式等** — 收到。
需要展开成明细，因为"边框"和"文本"各有多层含义：

- **边框**：`无/实线/虚线/点线/双线` × 线宽 × 颜色；**且必须能按边分别设置**（上/下/左/右独立，"只加下框线"是最高频操作），再往外扩是 Word 那套「外侧框线 / 内部横线 / 内部竖线」的批量套用。
- **文本**：内容 + 字体 / 字号 / 字重 / 颜色 / 水平对齐 / 垂直对齐 / 文字方向（横排/竖排）/ 缩进与内边距。**这一套和现有 `TextElement` 的属性几乎完全重合，应当复用同一份属性定义与渲染逻辑，不要另起一套。**
- **背景色**：单元格填充。若要更完整，可加"渐变/图案底纹"，但优先级低。
- 还有个你没提但绕不开的：**单元格内容的溢出策略**——文字超长时是自动换行撑高行、还是缩小字号适应、还是裁掉、还是溢出到相邻空格（Word 有"适应文字"）。这个直接决定行高是否会被内容改变，必须在数据模型里定下来。

**② 选中多个单元格，右键菜单可合并 / 拆分** — 收到。补充两点：
- 合并的前提是**选区是矩形**（Excel/Word 都要求矩形；非矩形选区合并的语义会让人困惑）。
- 合并后原内容怎么处理？主流做法是**只保留左上角单元格的内容，其余丢弃**（Word 会在合并时弹确认或直接保留左上）。要定。
- **拆分**需要指定拆成几行几列（Word 是这样），不是简单地还原成合并前——因为合并前的状态可能已经不存在了。
- 相邻扩展：**合并后跨页/跨行高怎么算**，以及合并单元格在拖行高列宽时的行为（拖到合并格涉及的某条列线，要整段一起动）。

**③ 右键当前行 / 列，前后插入整行或整列** — 收到。补充：
- 现在菜单里那两项是"末尾 +1"，要升级为**在上/下方插入行、在左/右侧插入列**（4 项），并保留"在末尾追加"的快捷入口。
- 既然有了"当前行/列"的概念，就需要**选中整行/整列的入口**（见 §3.B 补充项 1），否则"当前行"只能靠"活动格所在行"隐式推断。
- 还需要**删除行 / 删除列 / 删除整表**（与插入成对，不然误插不能撤）。
- 插入位置落在**合并单元格内部**时怎么处理（拒绝？还是按合并区外缘插入？）——建议按外缘插入，否则会破坏合并拓扑。
- 合计：插入行、删除行、插入列、删除列、删除表格。

**④ 表格右键与单元格右键不同，属性面板也不同** — 收到，且这条是架构需求（见 §2.2 缺口三）。
建议把上下文分成 5 类，各自一套菜单 + 一套面板：

| 上下文 | 菜单重点 | 面板重点 |
|---|---|---|
| 表格体（边框线/表格整体） | 插入行列、删除、表格属性、平均分布、清除内容 | 表格级：尺寸、外框线、对齐、自动调整、跨页、数据绑定 |
| 单元格（单个） | 插入图片/文本、合并拆分、边框、清除 | 该格：文本样式、边框四边、背景、对齐、内边距 |
| 行列头 | 插入上/下/左/右、删除行列、均匀分布、设为表头行 | 行高/列宽精确值、重复标题行（仅行） |
| 多格选区（≥2 格） | 合并、平均分布、批量设边框/背景、清除 | 选区共有属性（多值状态显示为"混合"） |
| 单元格编辑中（第 3 层） | 剪切/复制/粘贴/全选 | 文本样式（与文本元素一致） |

**⑤ 单元格右键中要有"插入"，可以插入图片** — 收到。这里需要你确认一个关键点：
"插入图片"是**把图片作为单元格内容**（图片按 `objectFit` 填进格子里，跟文本二选一），还是**图片元素漂浮在单元格之上**（图片是独立元素，只是位置恰好落在格子上）？
- 前者：图片受单元格约束，行高列宽变化时跟着变，会被裁切。语义干净，但表达能力弱。
- 后者：等于"把图片元素的坐标吸附到格子里"，图片和表格是并列的两个元素，插入后拖走也没关系。实现简单（能力已经全有了），但"表格里的图片"会散架。

我建议**前者**（单元格内容可择一为文本或图片），因为单据场景里"单元格里放个二维码/条码/签名图"是刚需，且要随表格走。
再往外一层：既然要放二维码/条码，**是否要把条码/二维码也作为单元格内容类型**？定位已定是数据表格，**条码/二维码几乎必然要**（标签/单据场景），建议 `content.type` 联合类型的扩展位从第一期就留（见 §1.5 约束 2）。

**⑥ 拖动修改行高列宽** — 收到。需要定义清楚：
- **拖拽热区**：行/列分隔线上（光标变 `col-resize`/`row-resize`），建议热区宽 6~8px，且**只在表格编辑态出现**，不要和元素缩放手柄抢。
- **拖拽粒度**：拖某条分隔线，只影响**相邻的两行/两列**（Word 语义：拖第 2 行的下边界，第 2 行变高，其余不动）；还是"整表等比"？建议前者。
- **多选时整批等宽**（Excel 语义：选中多列后拖一条线，所有选中列变同宽）——建议作为改进项，非首期。
- **双击自适应**：双击分隔线 = 按内容自动撑开，这是 Excel/WPS 的高频操作，**强烈建议一起做**（实现上需要测量文本宽度，可复用现有 `measureEditorHeight` 的思路）。
- **精确输入**：属性面板给行高/列宽的数值输入（mm）。约束关系**已定**：元素框总宽高 ≡ 列宽/行高之和；拖分隔线只改相邻两行/列（框不动），拖元素手柄等比缩放全部行高列宽（见 §1.5 约束 1）。
- **行高列宽的模式**：`固定值 / 最小值 / 自动`（Word 语义：`至少`= 内容撑高但不少于设定值）。至少"自动"和"固定"要区分，否则内容多了要么溢出要么把表格顶变形。

**模块 1：结构操作**（P0 除标注外）

**模块 2：单元格样式**（P0/P1）
6. **边框按边设置**（补充①，P0）+ **批量套用**：外侧框线 / 内部横线 / 内部竖线 / 无框线 / 全部框线（P1）。
7. **相邻单元格共享边的冲突规则**——两个格子相邻，各有自己的边框设置，那条共享线听谁的？**v4 已定：不做自定义裁决**，渲染层用 `<table>` + `border-collapse: collapse`，共享边由浏览器按 CSS 规范合并（更宽者胜 → 样式优先级 → 靠前者）。数据层仍把边框建模为"格四边"（这是表达能力的需要），但"听谁的"不再由代码回答。**P0，必须现在决定的事 —— 已决定，见 §9.3-2。**
   **v6 补充（这是个真 bug）**：只靠"浏览器合并"是不够的 —— 写入时只写自己那半边，CSS 的"更宽者胜"会让**调细 / 去掉全部失效**（邻格的默认线宽总是赢）。现在写入走 `writeBorderEdge`，把共享边**同时写进相邻两格**，两侧恒等，CSS 无需裁决。详见 §9.7。

31. **跨页时的边框处理**（被切开的那一行，上/下边框怎么画）。

**模块 8：数据能力**（P3 终局目标，见 §1）
32. **数据源导入**（Excel/CSV/JSON）+ **字段拖拽绑定到单元格**（标签软件的通用交互）。
33. **明细行重复**：数据每一条生成一行，行数运行时决定，表格高度自动增长并跨页。

## 4. 数据模型草案（已按 §1.5 预留，字段名待定）

现在的：

```ts
interface TableElement extends BaseElement {
  rows: number;
  cols: number;
  cellStyle?: { borderColor?; borderWidth?; padding? };  // 全表一份
}
```

撑不住合并，也撑不住逐格样式。方向（**扁平数组 + 显式合并**，与 ProseMirror 的 `tableCell(colspan, rowspan)` + `TableMap` 思路一致，业内验证过的模型）：

```ts
interface TableCell {
  /** 该格横跨的列数/行数，默认 1 */
  colspan: number;
  rowspan: number;
  /** 被左上角格合并覆盖的格子标记为 true —— 不删格，避免行列索引错位 */
  covered?: boolean;
  /** §1.5 约束 2：value 允许含 {占位符}，设计态原样渲染；type 留扩展位给 image/barcode */
  content?: { type: "text" | "image" | "barcode"; value: string; /* 文本样式… */ };
  style?: { backgroundColor?; border?: CellBorder; align?; vAlign?; padding?; writingMode?; wrap? };
}

/** §1.5 约束 3：行角色。第一期全是 "normal"，数据版靠它区分模板行与表头行 */
type RowRole = "header" | "detail" | "summary" | "normal";

interface TableElement extends BaseElement {
  /** §1.5 约束 1：绝对 mm。Σ colWidths ≡ width，Σ rowHeights ≡ height */
  colWidths: number[];
  rowHeights: number[];
  /** §1.5 约束 4：行高列宽的模式 */
  colWidthModes?: ("fixed" | "atLeast" | "auto")[];
  rowHeightModes?: ("fixed" | "atLeast" | "auto")[];
  cells: TableCell[];              // 长度 = rows × cols，行优先
  rows: number; cols: number;      // 派生缓存，便于校验
  /** §1.5 约束 3：行角色数组（与 cells 一样按行索引） */
  rowRoles?: RowRole[];
  /** 表头行数：前 N 行每页重复（服务 P1 的跨页表头重复） */
  headerRows?: number;
  /** §1.5 约束 3：明细模板行索引（数据版用，第一期空着） */
  detailRowIndex?: number;
  /** §1.5 约束 6：允许跨页断行 */
  allowBreakAcrossPages?: boolean;
}
```

两个模型上的取舍，先明确写出来免得后面吵：

- **为什么被合并的格子要保留（而不是从数组里删掉、只留 colspan）**：删掉的话 `cells[r*cols+c]` 的索引不再对应网格坐标，任何"第 3 行第 2 列是什么"的计算都要先做一遍拓扑推导，选区/命中检测/拖拽热区全部变复杂。保留 + `covered` 标记，索引永远是网格坐标，代价只是渲染时跳过被覆盖的格。
- **行高列宽为什么单独存数组而不是存进每个格**：行高属于"行"，存进格会立刻产生"同一行两个格行高不一致"的不一致状态。

### 9.3 实现层面的三处决定（请复核）

1. **旋转态下允许拖分隔线**（文档 §3.B-38 建议禁止，实际是"允许拖、但不吸附"）。
   理由：位移换算在元素局部坐标系里是**精确**的（与缩放同一套分解），不存在漂移；
   吸附则只在 0° 生效（转过角度后分隔线的纸张坐标不再是 `el.x + 前缀和`，吸了会错）。
   "允许但不吸"比"直接禁止"更宽容，且没有正确性代价。

2. **渲染用 `<table>`（v4 推翻 v3 的 div 网格方案）**。
   v3 的判断是"`<tr>` 的 height 是**最小**高度，内容一多行就自己涨，做不到 mm 精确定高"，
   因此改用绝对定位 div 网格绕开。**这个判断只对了一半**：
   `<tr>` 的高度是精确的，前提是**单元格里没有流内内容**。
   把内容层做成 `absolute inset-0`（相对定位锚点落在 `td` 上）之后，td 的"内容高度"归零，
   行高完全由 `tr` 的 height 决定 —— mm 精度保住了，且这套结构是浏览器表格布局的原生语义。
   配套两条缺一不可：`table-layout: fixed` + 显式 `<colgroup>`，把列宽钉死在数据上
   （auto 布局下内容会参与列宽计算，文字一长列就变宽，精度当场失效）。

   **换来的好处（按价值排序）**：
   - **为"表头行跨页重复"留下了唯一可行路径**。浏览器打印引擎对 table 有原生分页支持
     （前 N 行挪进 `<thead>` 即可逐页重复、`tr` 可设 `break-inside`），
     div 网格无论怎么写都拿不到 —— 而这正是数据明细表跨页的刚需（§1.5 约束 6）。
   - **共享边冲突不再需要自己裁决**。交给 `border-collapse: collapse` 后，相邻两格的边框
     由浏览器合并成一条线，规则遵循 CSS 规范（更宽者胜 → 样式优先级 → 靠前者），
     与 Word / Excel 表现一致。v3 里那个必须"双向对称"的 `resolveBorderEdge`
     （保证 `(r,c).bottom` 与 `(r+1,c).top` 解出同一个值）整个消失了 —— 那类隐患是
     "自己画线"才有的，现在从根上不存在。
     > **v6 追加**：这里最初漏了一层 —— 渲染侧不裁决 ≠ 写入侧可以只写半边。
     > CSS 的"更宽者胜"会吃掉"调细"和"去掉"，所以**写入时必须两格同写**（`writeBorderEdge`）。
     > 不变式没有消失，只是从"渲染时解出同一个值"变成了"写入时写成同一个值"。见 §9.7。
   - DOM 是语义化表格，导出 / 复制 / 打印读得懂；合并格由 `rowspan` / `colspan` 原生表达，
     不需要"累加宽高再绝对定位"。

   **代价**：
   - 拖列宽 / 行高时浏览器要重跑表格布局算法，比绝对定位重排慢。小表格（单据明细量级）无感。
   - 内容超出设定行高时仍被 `overflow: hidden` 裁切 —— 与 v3 相同，`atLeast` 未做（见 9.4）。
   - 边框冲突遵循 CSS 规范而非我们自定义：同宽不同色时取"靠前者"（即左上优先），
     与 §8 原先写的"同宽取右/下者"不同。**以浏览器行为为准**，且它更接近 Word 直觉。

   渲染层之外的一切不变：`colOffsets` / `rowOffsets` 前缀和仍要保留 ——
   选区框、活动格高亮、分隔线热区、行列把手都是**相对表格定位的浮层**，
   它们没有表格布局可依托（见 9.3-2 后的 `model.ts` 注释）。

3. **默认单元格字号定为五号（10.5pt）**。
   面板的字号下拉是 pt 档位，默认值若随手取一个毫米数（如 3.5mm ≈ 9.9pt），
   用户什么都不改也会看到"显示 10.5、实际 9.9"。基准对齐后两者一致。

### 9.4 为什么 `atLeast` 单独留了一批（不是漏做）

`atLeast`（内容撑高行）看起来只是一个 `min-height`，实际是一条**测量回路**：
渲染后量内容高度 → 若超过设定值则改行高 → 改行高会改变元素框（`Σ rowHeights ≡ height`）
→ 触发重渲染 → 再量。这条回路一旦写成"每帧都跑"，就是典型的
"测量 → 写入 → 重渲染 → 再测量"死循环（项目在拖拽上已经踩过同类的坑）。
它需要：只对 `atLeast` / `auto` 行生效的 ResizeObserver、写入前的**收敛判断**
（差值小于阈值就不写）、以及元素框被动增高的连锁处理。
值得做，但值得**单独一批做对**，不适合塞在 P0 尾巴上凑数。

> v4 补充：改回 `<table>` 之后这条回路**反而变短了**。
> 绝对定位 div 网格里"内容需要多高"只能靠测量；而表格布局里，
> 只要对 `atLeast` 行**不设 `tr` 的 height**（或设成 `min-height`），浏览器自己就会把行撑开，
> 我们只需在稳定后**读回实际行高**并写进 `rowHeights`。
> 也就是说从"测量内容 → 推算行高"退化成"读取浏览器已经算好的结果"，
> 死循环的风险随之下降。`fixed` 行照旧走上面的精确路径，两者互不干扰。

### 9.5 验收后修掉的三个 bug（前两个是"默认行为被拦"的连锁反应）

**① 点别的单元格退不出文本编辑**

`onCellPointerDown` 里为框选加的 `preventDefault()`，拦掉的正是浏览器"按下鼠标即转移焦点"这个
默认行为。焦点不走 → `textarea` 不失焦 → `onBlur` 不触发 → 编辑态一直挂着。
修法是**显式收**（`stopCellEditing()`），不再指望失焦。内容由 `@input` 实时写进 store，
所以这里不需要任何"提交"动作。

**② 右键菜单点别的单元格不消失（本记录里唯一一个架构级问题）**

关不掉的原因有两层，缺一不可地叠在一起：

- **reka 的关闭挂在 document 的冒泡阶段。** `DismissableLayer` 用的是
  `addEventListener("pointerdown", handler)`，**没有 capture**。而本项目元素内部的
  pointerdown 处处 `stopPropagation`（挡的是画布根的"点空白取消选中"），
  于是"点在另一个元素/单元格上"这类事件**永远到不了 document**，菜单关不掉。
  这是"用 stopPropagation 达成一个具体目的"的典型代价：它顺手切断了 document 层的
  一切监听 —— 菜单关闭只是第一个撞上来的。
- **ContextMenu 默认 `modal`，reka 会把 `document.body` 的 `pointer-events` 设成 `none`。**
  菜单开着时画布上的元素全都点不中（事件目标退化成 `<html>`），
  于是"点下面那个元素"和"关掉菜单"变成互斥的两件事。

修法是三条独立的措施（任一条失效都还有其余兜底）：

1. **画布根改判落点，元素内部不再拦冒泡**：`ElementWrapper` 去掉 `@pointerdown.stop`，
   改为根节点带 `data-design-element`，画布根的 `onRootPointerDown` 用
   `closest("[data-design-element]")` 判断"点在元素内"就放行。
   表格的单元格、分隔线、行列把手同理去掉 stop —— 它们在表格编辑态下本来就靠
   `ElementWrapper` 的 `tableEditing` 分支让位，stop 是多余的。**（`GuideLines`、
   `TextElement` 的 textarea、各手势手柄的 stop 保留：它们拦的不是 document，是别的内层手势。）**
2. **`:modal="false"`**（两处菜单）：桌面右键菜单本就该是非模态的，点哪儿就作用到哪儿。
3. **新增 `ContextMenuAutoClose.ts` 哨兵**：放在 `<ContextMenu>` 内，通过 reka 公开导出的
   `injectContextMenuRootContext` 拿到 `onOpenChange`，在 **document 的 capture 阶段**
   监听左键 —— capture 是路径第一站，早于任何 stopPropagation，不依赖任何人配合。
   点击落在 `[data-dismissable-layer]` 内（菜单自身）时不关，保护菜单项的 click。

> 关闭只写状态，Vue 的 DOM 更新是异步的，所以事件仍会完整传播到下面的元素上：
> "点一下既关菜单、又切到那个单元格"成立，不会吞掉这次点击。

**③ 点单元格不出现选中蓝框（②的连带）**

表格 root 上挂着"点表格空白 = 清空选区"的 handler，它原本**无条件**执行
`stopCellEditing()` + `setCellRange(null)`。以前单元格自己 `stopPropagation`，root 收不到；
② 把单元格的 stop 去掉之后，点单元格的事件**冒泡上来**了，执行顺序变成
"td 刚选中 → 冒泡到 root → 当场抹掉"，同一帧内自己选中自己清，看着像完全没反应。

根子是**父容器的清理型 handler 假设了"事件到达我 = 落点在我身上"** —— 这个假设只在子元素
主动 stop 时成立，stop 一拿掉它就是个静默的错误。修法：清理动作先判落点
（表格 `e.target === rootRef.value`，画布 `closest("[data-design-element]")`）。
这同时修好了"点列头整列选中"——它也是同一个受害者。

### 9.6 多实例才暴露的两个坑（画布上出现第二个表格后才现形）

**① 两个表格互相联动（严重：改一个，另一个跟着变）**

`createElement` 对载荷做的是**浅展开** `{...partial}`，而 `partial` 来自素材清单里
`mat-table.defaults` —— 那是**模块级常量**，`createTableDefaults(...)` 在模块加载时只算过一次。
于是两个表格"两份外壳、一份内脏"，`cells` / `colWidths` / `rowHeights` 是同一个数组。

顺带一个比原症状更狠的后果：`表格1.cells === defaults.cells`，**改 A 表改的就是那份模块级模板**，
之后拖出来的每个新表格都带着被污染的行数，**只有刷新页面才恢复**。

修法：`createElement` 统一过 `cloneElementPayload`（`structuredClone(toRaw(v))`）。
修在唯一入口上，所以**线条**一并受益 —— 它其实也中招（两个线条共享 `start` / `end`），只是没人报。

> 结论：**素材清单的默认值是"单份模板"，凡进 `elements` 必须先深拷贝。**
> 判断口诀：别用"看起来一样"解释串改 —— 现象是"两份数据是同一个对象"。

**② 有两个表格时双击无法编辑单元格**

第 3 层状态 `cellEditing = { r, c }` **不含"哪张表"**，而判断"这一格该不该渲染输入框"
只比坐标。两张 3×5 的表格坐标必然重合 → 编辑 A 表某格时，B 表同坐标也渲染出一个 textarea →
两个都去 `focus()`，后者顶掉前者 → 前者触发 `blur` → `onCellBlur` 只比坐标（命中）→
`stopCellEditing()` → **刚开好的编辑被自己关掉**。

修法：给 `isEditingCell` / `editingKey` / `onCellBlur` / `onCellInput` 补上
"本表就是活动表"（`tableEditingId === element.id`）的门禁，并全量审计了其余消费点。

> 结论：`cellRange` / `activeCell` / `cellEditing` **天生不知道自己在哪张表里**。
> 凡读第 2/3 层状态的 computed 或 handler，第一行先问"我是那张活动表吗"。

### 9.7 边框设置"改了不生效"（根因：共享边只写了半边）

现象（老板报）：线型 / 线宽 / 颜色改了都不生效，只有点"应用到那条边"才生效；
线宽还只能往宽了调，调细没反应。**是两个独立的原因叠在一起** —— 一个交互设计问题，
一个真 bug。

**① 面板的心智是"先配笔、再应用"。** `draft` 是面板内的一份局部状态，改它只改这份局部状态，
只有点侧边按钮才写进 store。→ 改成**批改器**：面板显示的就是选区当前值，改任意一项**立刻**重涂。

**② 共享边只写了"自己那一半"（"只能调宽"的真正原因）。**
渲染层每格只写自己四边，共享边交给 `border-collapse` 合并，而 CSS 的裁决规则是
**更宽者胜** —— 邻格那半边通常是**表格默认的 0.26mm**，于是：

| 操作（旧） | 结果 |
|---|---|
| 把右边调细到 0.1mm | 邻格 0.26mm 胜出 → **看着像没反应** |
| 把右边"去掉"（旧代码是**删掉属性**） | 自己回落成默认 0.26mm → **线原样还在** |
| 把右边调粗到 1mm | 自己胜出 → 生效（所以只有"调宽"能用） |

修法：新增 `writeBorderEdge`，把这条边**同时写进共享它的两格**（镜像到邻格的对面边）。
两个半边值恒等，CSS 就没有可裁决的余地。合并格横跨多格时，镜像到它跨过的**每一格**。

> 推论：**"删掉属性"不等于"关掉这条边"** —— 删属性只是回落表格默认（仍然可见）。
> 关边必须写**显式的 `{ style: "none", width: 0 }`**，且两侧同写，线才真的消失。

**目标集合是"可见的边"，不是"选区内所有格的所有边"。**
后者在用户只想把外框线改个颜色时，会把已经清掉的内部线一起**复活**。清线是"无框线"按钮的活；
改属性只重涂**已有且可见**的线。混选时只写被改动的那一个属性，其余保留每条边自己的值
（A 边 3px、B 边 1px 时改颜色，不会顺手把宽度也统一掉）。

顺带修掉的三处：

- 侧边按钮的激活态改读 `ownBorderEdge`（含表格默认）—— 以前只看**显式设置**，
  新建表格四边明明有线、按钮却全是"未激活"。
- 侧边按钮改为**选区外缘**语义（上 = 首行的上边…），与"外框线"一致 ——
  以前是"选区内每一格的该侧"，在 3×3 选区里点"上"，内部两行也会跟着长线。
- 删掉 `resolveBorderEdge` / `resolveCellBorders`（v3 遗留的"自己裁决共享边"死代码）。

**验证方式**（临时脚本，esbuild 打包真实 `model.ts`，跑完即删）：脚本里复刻 CSS 的
"更宽者胜"裁决，实测旧写法调细到 0.1mm 后该线的实际线宽仍是 **0.26mm**（症状复现），
新写法为 **0.1mm**；旧写法"删属性"后线**仍在**，新写法"显式 none"后线**消失**；
并断言写入后 `(r,c).bottom` 与 `(r+1,c).top` **恒等**（横竖两个方向不一致处数均为 0）、
合并格横跨三列时上方三格的 `bottom` **全部**被镜像。

### 9.8 插入列改为"表格总宽不变"（v7，老板要求）

现象：左/右插入列时表格整体变宽，多插几列就顶出内容区右边界，用户还得回头一列列缩。

原实现是 `el.colWidths.splice(a, 0, borrowSize(...))` —— 新列**从表格外面长出来**，
而 `syncTableGeometry` 又把 `el.width` 回算成 `Σ colWidths`，于是元素框跟着一起宽。

改成**在内部重新分配**，两步（`insertCol`）：

1. 新列先按**相邻列的宽度**挂进去（新列与邻居同宽，视觉上最好理解；插在最左借右邻、
   追加到末尾借左邻，`borrowSize` 原本就是这个语义）；
2. 整组等比缩回**原来的总宽**（`fitTracks`）。等宽表插完还是等宽（100 → 3 列各 33.33 →
   4 列各 25），手工调过比例的表保持原比例。

- **为什么用等比而不是"从一个邻居那儿切一半"**：局部切法在等宽表上会得到
  `[33.33, 16.67, 16.67, 33.33]` 这种参差结果，而"在内部变"这件事对所有列应当一视同仁。
- **`fitTracks` 的存在理由就是 MIN_TRACK**：纯等比（`scaleTracks`）在"已有列贴着 2mm"时
  会把窄列压到 2mm 以下，插几次就出现既看不见也点不中的缝。所以缩放后若跌破下限，
  抬回下限，抬出来的量再从"还有富余的列"里按富余比例扣回，末尾把舍入残差贴到最宽的项上 ——
  `Σ ≡ width` 这条不变量在任何分支下都保持。
- **插入行不动**：行是内容量（明细表插一行就该变高），宽度才是版面约束。两者语义不同，
  刻意不做成对称 —— 若哪天要给行也加"总高不变"，那应当是另一个开关而不是顺手的默认。
- **删除列同样没动**：删除后表格变窄仍是当前行为（用户删列往往正想腾出宽度）。
  要"删列也保持总宽、把宽度匀给其余列"的话是一行 `fitTracks` 的事，但那是另一个决定。

**验证方式**（临时脚本，Node 22 直接跑真 `model.ts`，跑完即删）：29 条断言全绿 ——
等宽表 3→4 列得 `[25,25,25,25]` 且总宽 100 纹丝不动；插最左 / 追加末尾 / 连插 20 列
（180mm → 23 列）总宽均保持原值、`Σ colWidths ≡ width` 严格成立、无列低于 `MIN_TRACK`；
手工不等宽表 `[70,30]` 插入后仍保持宽窄关系且新列与相邻列等宽；
`[98,2]` 这种贴边表插入后得 `[49,49,2]`（下限抬升 + 富余扣回生效）；
跨插入线的合并格 `colspan` 正确 +1、被盖住的新格标 `covered`。

### 9.9 整表批量改行高（v8，老板报"只能一行行改"）

现象：想统一调整所有行高，只能"选中整行 → 改数值"重复 N 次。

**是两层原因叠出来的**：

1. 表格编辑态下整个元素级面板被**替换**成单元格面板（需求 ④ 的粒度切换），
   于是"位置 & 尺寸"里的**高度**（唯一能整体缩放的入口）在编辑表格时不可见；
   → _v9 起改为「表格 / 单元格」两组并存，这条已不成立，见 §9.10。_
2. 单元格面板里的行高输入框带 `v-if="rowHeight !== null"` —— 只有**选中整行/整列**才渲染
   （混合选区确实没有"这一行"可言），所以随手点一格时面板里连行高都找不到，
   必须先点行把手，改完再点下一行把手。

**改法**：在单元格面板最前面加一项**「整表行高 / 列宽」**，不依赖选区、永远可用，
两个字段分别是"每行行高"和"每列列宽"，写入走新增的 `setAllTracks(el, axis, value)`。
（**→ v9 已搬到表格级分组，见 §9.10**：挂在单元格面板只是权宜之计，粒度不对。）

- **显示值取现有尺寸的平均**：全部相等时它就等于那个值（多数情况），参差时给个代表值 ——
  用户改一次就把整表拉平，这正是本控件的用途；说明文字里点明"当前不一致时显示平均值"。
- **清空输入框不当作 0**：`setAllTracks` 显式忽略 `null` / `undefined` / `NaN`，
  否则编辑过程中的中间态会被夹成 `MIN_TRACK`（清一下输入框整表缩成 2mm）。
- 行高/列宽模式一并回落 `fixed`（`atLeast` 还没做，留着旧模式会在撑高回路接上时行为不一致）。

**至此"改轨道尺寸"有三个语义，靠「总尺寸变不变」划清**（都在 `model.ts`，别混用）：

| 入口 | 行为 | 表格总尺寸 |
|---|---|---|
| `resizeTrackPair`（拖分隔线） | 相邻两轨互相让位 | 不动 |
| `distributeTracks`（右键·平均分布） | 选区内轨道等分现有总长 | 不动 |
| `setAllTracks`（面板·整表行高/列宽） | 每条都改成 value | = 数量 × value |

另有一条**不进入编辑态**的路径：元素级面板的"高度" / 拖元素缩放手柄 → `updateElement`
里对表格走 `scaleTracks` 等比缩放全部行高（比例不变、总尺寸变）。三条路互不冲突。

**验证方式**（临时脚本，Node 22 直接跑真 `model.ts`，跑完即删）：17 条断言全绿 ——
5 行表统一 8mm 后总高 40mm、总宽不动；统一列宽 25mm 后总宽 75mm、总高不动；
`[4,12,6,8]` 一次拉平成 `[7.5×4]`；3.33mm × 3 行这类除不尽的每行**严格相等**且 `Σ ≡ height`；
低于下限夹到 `MIN_TRACK`；`null` / `undefined` / `NaN` 被忽略（行高保持原值）；
`rowHeightModes` 全部回落 `fixed`；统一列宽后再插列，总宽不变的约定仍成立。

### 9.10 面板按粒度重新分组：表格 / 单元格（v9，老板指出"整表的东西不该放单元格面板"）

老板的疑问：整表行高/列宽是**表格级**的东西，为什么长在单元格属性面板里？

**判断：他是对的，而且这暴露了 §9.9 的权宜性质。**
根因是面板切换机制 —— 编辑态下 `ElementProperties` 用 `v-if="activeTable"` 把**整个**元素级
Accordion（含"位置 & 尺寸"和"表格属性"）替换成了单元格面板。也就是说**编辑态下"表格属性"
根本不存在**，所以 §9.9 只能把整表控件挂在单元格面板里。

**改法（结构）**：编辑态面板从"整体替换"改成**按粒度分成两组并存**：

```
[正在编辑表格 · 退出]
表格     ← 表格级：与选区无关，任何时候可用
  位置 & 尺寸          （X / Y / 宽度 / 高度）
  整表行高 / 列宽       （setAllTracks）
单元格   ← 单元格级：全部作用于当前选区
  [选区信息条 A1:B2 可合并]
  行高 / 列宽（选区）/ 文本 / 对齐 / 边框 / 填充 & 边距 / 合并 / 拆分
```

- 早先"替换"的代价：编辑表格时改不了表宽、改不了整表行高，得先退出编辑态 ——
  而"统一所有行高"恰恰是**编辑表格时**最想做的事，等于把功能藏到了最不需要它的时机。
- 分组标题用 `text-muted-foreground text-xs font-medium`，与元素面板的 section 标题同款。
- **不追加新逻辑**：`setAllTracks` 等一行没改，只是把折叠项从 `TableCellProperties`
  搬到新的 `TableProperties.vue`，单元格面板净减一个折叠项。

**顺带抽出的 `ElementLayoutSection.vue`（位置 & 尺寸）**：它现在有两个宿主 ——
非编辑态的元素面板、编辑态的「表格」组。两个宿主下 `selectedId` 都指向目标元素，
所以组件内部自取 `store.getElement(store.selectedId)`，不传 props；`id="element-x"` 等
在同一时刻只会渲染一份（两个宿主互斥），不冲突。

**一处必须记住的写入路径差异**（搬控件时最容易踩）：

| 想改什么 | 走哪个 action | 原因 |
|---|---|---|
| 表格总宽 / 总高 | `updateElement` | 内部按 §1.5 约束 1 调 `scaleTracks` 等比缩放全部列宽/行高 |
| 整表行高 / 列宽 | `updateTable` | 走 `setAllTracks` + `syncTableGeometry` 回算总尺寸 |

**反了会静默失效**：从 `updateTable` 里写 `width` 会被随后的 `syncTableGeometry`
覆盖成 `Σ colWidths`，看着就是"输入框改不动"。

**验证方式**：4 个改动模块 `curl` 全 200、`eslint` 0 错误；编译产物里
`TableProperties` 含 `setAllTracks` / `table-tracks` / `uniformHint`，
`ElementProperties` 已引用两个子组件，`TableCellProperties` 中
`table-size` / `uniformRowHeight` **出现 0 次**（确认旧位置已清干净）。
**未做浏览器验证**，需老板手点：编辑表格时"表格"组能改表宽/整表行高、"单元格"组的选区操作不受影响。

### 9.11 行列把手标出列标 / 行号（v10，老板要求）

老板看到编辑态下表格上方、左侧的蓝色把手条，问能不能标出 ABCD / 12345。

- `colLabel`：`0→A … 25→Z、26→AA、27→AB`（Excel 式，不是 base-26 —— `Z` 之后是 `AA` 而不是 `BA`）。

### 9.12 合并格双击后选区背景只盖一角（v11，老板报"蓝底只有一个单元格有"）

**现象**：两个单元格合并后双击进文本编辑，**蓝色边框是完整的**（盖住整个合并区），
但**蓝色背景只盖住合并区的一角**。单击选中同一个合并格时两者都是完整的。
老板明确说"单击是对的，我说的是双击选中背景色不对"—— 这句话把事情从渲染层引开了。

**根因**：两层高亮的"扩张责任"不一致。

| 高亮 | 来源 | 是否扩张 |
|---|---|---|
| `selectionRect`（`bg-primary/10` 蓝底） | 直接读 `store.cellRange` | **不扩**，存什么画什么 |
| `activeRect`（`border-primary border-2` 蓝框） | `rangeOfPoint(el, activeCell)` | **内部自己扩过** |

而双击 → `startCellEditing(r, c)` 里写的是：

```
this.cellRange = { r1: r, c1: c, r2: r, c2: c };   // ← 1×1
```

于是 `cellRange` 只覆盖合并区的宿主格一个网格坐标，蓝底按它画 → 只有一格宽；
`activeCell` 虽然也是同一格，但 `activeRect` 自己过了 `rangeOfPoint` → 蓝框是整格。
**"框完整、底残缺"这个不对称，就是两条路径扩张责任不一致直接长出来的形状。**

这条不变量在别处都是遵守的：点选走 `rangeOfPoint`（`onCellPointerDown`）、框选走
`normalizeRange` + `expandRange`（`useDrag.onMove`）—— `cellRange` 是"当前选区"，
任何进入系统的路径都必须先扩张到"要么整格在内、要么整格在外"。**只有双击这条漏了。**

**改法**（`store/modules/design.ts`，只改两处赋值）：

```
const range = clampRange(expandRange(el, rangeOfPoint(el, r, c)), el);
this.cellRange = range;
this.activeCell = { r: range.r1, c: range.c1 };
this.cellEditing = { r: range.r1, c: range.c1 };
```

- 顺带把坐标归一到合并区的**宿主格**（左上角）：`cellEditing` 是给渲染层比对 td 坐标用的，
  而 `td` 只画在宿主格上（被覆盖的格不渲染）。双击落在被覆盖坐标时（理论上不会发生，
  但函数是公开的）也能正确落到可见的 td。
- `moveActiveCell` 是同一类违反（把 1×1 交给 `setCellRange`，而它**只夹取不扩张**），
  虽然目前没有调用方（键盘导航未做），一并补上 —— 否则这条不变量留着一个已知缺口，
  将来接键盘导航时会以完全相同的方式复现。

**改法之外还值得记的**：`expandRange` 对"被覆盖的坐标"也是对的 —— `buildTableMap` 会把
每个被覆盖坐标都指回它的**宿主格 ref**，所以从小格子起点也能迭代出整个合并区（迭代到不动点）。

**验证**（临时脚本跑真 `model.ts`，Node 22，跑完已删）：22 条断言全绿 ——
120mm×4 列表中合并 (0,0)-(0,1) 后，**旧行为蓝底宽 30mm（正好一半，复现现象）**、
新行为 60mm、且与 `activeRect` 几何完全一致；从被覆盖点 (0,1) 双击时旧行为蓝底还
**偏移到 30mm 处**（跑到合并区中段），新行为归零到宿主格；纵向合并、2×2 合并、
贴右下角的合并区都不越界；**回归项**：无合并时 12 个普通格新旧行为完全一致
（不引入任何副作用）。`curl` 200、`eslint` 0 错误。
**未做浏览器验证**，需老板双击合并格确认蓝底铺满整格。

### 9.13 线宽：默认值 1px、px 显示口径、未设置字段的显示（v12，老板报两个数不对）

老板报了两个数：**"表格线宽默认怎么是 0，应该为 1"**、**"单元格的边框默认是 0.98"**，
并自己给出了诊断："应该是转换的小数问题，0.264 应该是 1"。诊断是对的，
但**这两个数各有各的根因**，不是同一处：

| 位置 | 看到的值 | 根因 |
|---|---|---|
| 表格元素级面板「默认边框宽度（px）」 | `0` | `cellStyle.borderWidth` **从没设过** → 面板 `Number("") \|\| min \|\| 0` 落到 0；而渲染实际走 `DEFAULT_BORDER_WIDTH` |
| 单元格面板「线宽（px）」 | `0.98` | `round2(mmToPx(0.26))` —— 存的是"约等于 1px"的 0.26mm，且取整只留 2 位，0.9827 显示成 0.98 |

**三处改动，一一对应**：

1. **默认值改成精确 1px**：`DEFAULT_BORDER_WIDTH` 由 `0.26` 改为 `25.4 / 96`（≈0.264583）。
   原注释写"0.26mm ≈ 1px"—— 近似本身没错，但线宽 UI 的单位是 **px**，
   近似值换算回来就是 0.98px，面板上看着像"默认值本身是残的"。
   用字面量而不是 import `lib/utils` 的 `MM_PER_PX` 是有意的：`table/model.ts` 要保持
   **零运行时依赖**（只用 `import type`），才能脱离 Vite 直接拿 Node 跑验证；两者同源。
2. **px 显示统一走 `roundPx`（1 位小数）**：`lib/utils.ts` 新增，与既有的 `roundPt` 对称 ——
   pt 那一侧早就定了"UI 用标准档位、存储不 round"的规矩，px 这一侧漏了。
   两个面板（元素级 / 单元格级）现在共用同一条取整口径，不会再出现"同一根线在两处显示不同的数"。
   保留 1 位小数是为了还能表达 0.5px 发丝线。**存储的 mm 依然不 round**（打印精度不被显示层吃掉）。
3. **属性面板新增 `fallback`**（`PropertyFieldConfig.fallback`）：字段**未显式设置**时显示
   "生效默认值"，而不是 0 / 空。用在表格的「默认边框宽度」（→ `DEFAULT_BORDER_WIDTH`，显示 1）
   与「默认单元格内边距」（→ `DEFAULT_CELL_PADDING`，显示 0.5）上 ——
   内边距是同一类问题、同一个位置，一并修了。
   **fallback 只用于显示，不写回元素**："没设过就是没设过"，这样把它改回默认值不会把显式值钉进数据。
   顺带把该字段步进由 0.1 改为 0.5，与单元格面板的线宽步进一致（渲染层有 0.5px 下限，
   更细的步进没有意义）。

**关于浮点尾差**：`(25.4/96) × (96/25.4)` 在 IEEE754 下是 `1.0000000000000002`，
所以渲染出的 CSS 是 `1.0000000000000002px`。**不为这个尾差改渲染层**：
浏览器照常解析，面板显示与 `roundPx` 都已收敛成 1，动渲染路径不值得。
